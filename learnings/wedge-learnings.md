# Wedge Learnings

Accumulated aesthetic-direction learnings from `/wedge` runs. Absorbed from project memory via the `/forge` cycle.

These are universal aesthetic principles that survive across projects — not project-specific Touchstone choices. Project Touchstones live in their own repos; this file holds what the council has *learned* about driving the wedge well.

## Visual Decisions Need Visual Artifacts — One Preview, at Every Stage (2026-04-30 → 2026-07-04)
**Learning**: A user cannot choose an aesthetic from prose. Direction Cards, and multi-choice text naming hex codes and font names, ask them to imagine the result; typography pairings, palettes, and signatures only land on a real page at real scale, and rendering exposes failures (a pairing that doesn't hold, a signature flat at scale, motion that overstates) before the commit instead of after. Render every candidate at production craft and assemble the candidates into ONE file with a selector, never N files: same viewport, same scroll position, same font-loading state, deep-linkable per candidate. One-at-a-time viewing also stops the user averaging two directions in their head, which reinforces Commit-to-ONE. Discarded candidates stay behind their tabs as the historical record. The rule holds at every stage, not just the direction pick: once a layout skeleton is approved, later palette/type/layout choices are rendered as live toggles on that same screen (CSS-variable skin classes, a small utilitarian switcher bar, URL-param deep links per combination) — never as a prose menu. Trade-off accepted: ~1.5× cost per apprentice (spec + scoped fragment) for a seen decision over an imagined one. The mechanics (scoped fragments, isolated frames, assembler script) live in the wedge SKILL Heats 2-3; this entry is the why, plus the refinement-stage rule the SKILL does not yet carry.
**Apply when**: Any council-style or refinement-stage aesthetic choice — direction pick, palette, type, layout variants. Build the preview; do not describe the options.

## Soul Brief Beats Fielded Brief; Lens Beats Family×Tone (2026-05-04)
**Learning**: Cross-project convergence in a design council is manufactured by the briefing machinery, not by the products. Three causes compound: fields flatten soul (metaphor, sensation, weight, and anti-aesthetic do not survive a label like "audience posture: contemplative"); a fixed archetype shelf has the gravity of the subculture it was assembled from, so independent apprentices land in the same safe slots; and the same brief-plus-shelf run across different products yields visibly similar A/B/C triads. Fix it at the source, in three moves: a prose brief (what it IS, what it ISN'T, examples from outside the design domain, the defaults the model would reach for given THIS product); a per-product interpretive lens as the commission, with the shelf demoted to optional vocabulary; and a mechanical rhyme audit on the rendered fragments before the user sees them — apprentices believe they diverged while their fragments rhyme structurally. Naming what the product ISN'T discriminates better than naming what it is. Cap the respawns: repeated rhyme means the brief is thin, not the apprentices. The procedure lives in the wedge SKILL (Soul Before Vocabulary, Heats 1-2, anti-convergence audit).
**Apply when**: Designing any skill where N agents interpret one product's identity — prose brief with anti-aesthetic and outside-domain references, per-product frames over fixed menus, deliverables that cite the references that shaped them, and a convergence audit before assembly. Trade-off accepted: a longer brief heat and larger apprentice prompts for substantially more divergence.

## Dual-Accent Structural Systems Need Explicit Normative Documentation (2026-05-30)
**Learning**: Some directions use two accents that are both structurally required rather than "dominant + secondary" — e.g. a bilingual product where each script-world owns one accent and the tension between them is the design itself. Token YAML carries values, not intent: a downstream agent will pick a "main" accent and demote the other, collapsing the structure. The DESIGN.md must preempt that in four places: (1) name both under `colors:` with role descriptions that state structural purpose ("primary-script accent — the first script-world"), never "secondary accent"; (2) a Do — let `{colors.script-a-accent}` and `{colors.script-b-accent}` appear on the same surface simultaneously; their tension is structural, not a contrast problem; (3) a Don't scoping each accent's territory (e.g. don't use `{colors.script-b-accent}` on interactive elements — it belongs to the second-script text voice only); (4) note both accents' WCAG contrast ratios against the surface, so a builder doesn't swap them for one "safer" accent. Corollary — layout-as-translation: a bilateral two-column layout reads as "original | translation" to anyone familiar with multilingual publishing; the Do's and Don'ts must name that risk and prohibit the labels that trigger it ("Original" / "Translation"). The disambiguation belongs in the spec, not in the implementation.
**Apply when**: Any Touchstone whose chosen direction uses more than one accent colour for structural rather than decorative reasons — verify the DESIGN.md prose calls out the multiplicity explicitly, with a rationale and a guardrail in Do's and Don'ts.

## Tool-Register Products Need Tool-Register Touchstones — Two Faces, Density With Discipline (2026-07-04 → 2026-09-23)

**Learning**: When the product being wedged is a working tool (admin surface, task queue, enumerated lists, oversight or monitoring dashboard, anything a user keeps open all day), council apprentices default to editorial landing-page register: hero display type, scrolling composition, poetic copy, generous air. A founder evaluating a tool reads this as pretentious fluff with no functionality. Bind REGISTER explicitly in the Soul Brief: tool-register products get tool-register touchstones — single viewport, no page scroll, no hero, no marketing copy, information density as the virtue, aesthetic carried by type/ruling/color rather than layout theatre. "Calm/leavable/glanceable" must be disambiguated: a glanceable TOOL is dense (everything visible at once), not airy — apprentices reliably misread it as whitespace poetry. The target posture is density-with-discipline: dense professional data tables whose calm comes from hierarchy (size, weight, tabular alignment, one signal colour) rather than emptiness — and not ticker-wall maximalism either. Ground the density in domain research (how expert tools lay out the same data) rather than inventing it. The register rule is surface-scoped, not absolute: spacious presentation works for landing pages but kills the core business flow. Therefore the Touchstone ARTIFACT should carry two first-class faces from one token set — a Landing face (spacious, editorial) and a Core Flow face (dense, real UI grammar: nav, stat tiles, tables, charts) — because a landing-only Touchstone gets inherited by builders into working screens where it misrepresents and kills the application flow. Core Flow face is the primary commission for tool products.

**Apply when**: Any /wedge run on a product whose primary surface is a working screen. Soul Brief must carry a binding Register section; Heat 5/6 should produce both faces; the anti-convergence audit treats register mismatch as a soul-transmission failure.

## Councils Search, They Don't Single-Shot — Expose a Regenerate Branch, Never Self-Pick (2026-07-04)

**Learning**: Even a sharp brief and divergent lenses can produce N directions where none lands. When the user rejects the full slate, the orchestrator must not synthesize a committed direction to keep momentum — an unchosen aesthetic gets challenged the moment it appears. Commit-to-ONE governs the ARTIFACT, not the CHOICE: the user stays the taste gate, and the recovery step is another user-facing choice rendered as clickable options. So the verdict step carries a third branch beside pick-one and hybridize: regenerate with structured feedback (lens-level or execution-level miss? which defaults did the council reach for that must now be named binding? which brief section was thin?), a revised brief, and a versioned new preview, with prior previews preserved. Cap the cycles at two; hitting the cap means the upstream source is misaligned and the skill halts and says so. Better N rounds and a lived final artifact than one round and an artifact the user quietly drifts away from. Mechanics: wedge SKILL Heat 4.

**Apply when**: Any divergent-fan-out design where the user is the final taste-gate, aesthetic or otherwise — expose "regenerate with feedback"; never resolve a full-slate rejection by silent synthesis.

## Soul-Driven Convergence Is Legitimate — Don't Respawn for Manufactured Difference (2026-09-23)
**Learning**: When the product's soul dictates a colour law (e.g. colour reserved for state changes, never for decoration or emotional emphasis), independent council apprentices will converge on the same palette family (warm ground + one reserved signal). That is convergence on the essence, not on a generic default. The anti-convergence audit should pass it and flag only default-driven rhyme; respawning pushes apprentices away from the soul toward difference for its own sake.
**Apply when**: A design council's candidates converge — check whether the shared trait traces to the Soul Brief before treating it as slop.

## Theme Governs the Calm State; the Alarm State Is Theme-Independent (2026-09-23)
**Learning**: For any product with a calm→alarm transition, the light/dark theme governs only the calm surface; the alarm state floods to ONE fixed critical palette in every theme. An alarm doesn't care about the viewer's colour preference, and a single alarm identity strengthens the "becomes a different object" signature.
**Apply when**: Designing theming for a product with a critical/alarm state.
