## h-full vs min-h-full in Scroll-Container Chains (2026-06-02)
**Learning**: In a flex-column scroll container chain, `min-height: 100%` does NOT establish a height reference for children's `justify-center` — only `height: 100%` does. For cards that must both center short content AND allow expansion for dense content: chain is `overflow-y-auto (fixed height)` → `h-full` wrapper → `min-h-full` content div. The `min-h-full` expands for dense content (overflow handled by scroll container), while `justify-center` still works for short content because the div fills to its min-height.
**Apply when**: any scrollable card with vertically centered content that can also overflow.

## Scroll Content Inside Decorated/Framed Backgrounds — Structural Inset, Not Percentage Padding (2026-06-02)
**Learning**: When a scroll area's background image has decorative zones (borders, corner ornaments, framing), CSS padding-based safe zones fail — scrolled content flows freely through those zones regardless of padding. The reliable solution is a **structural inset**: outer div (`overflow-hidden` + background image), inner div (`position: absolute; top: X%; bottom: Y%; overflow-y-auto`), so content is physically bounded within the safe zone. CSS padding, `mask-image`, and gradient overlays are incomplete substitutes. Part of *why* padding fails for vertical clearance: **CSS percentage padding is width-based, not height-based** — `padding-top: 8%` (Tailwind `pt-[8%]`) computes to 8% of the containing block's *width*, not its height. On a tall portrait card (e.g. 360×640), `pt-[8%]` = 29px, far less than 8% of the 640px height (51px). If you must use percentage padding for vertical clearance, verify the absolute pixel equivalent and prefer `vh`-based or fixed-pixel values for height-sensitive clearances.
**Apply when**: any scrollable UI panel with a decorated/framed background image where content must not enter the decoration zone; and any vertical safe-zone or clearance calculation using percentage padding on portrait/mobile layouts.

## Show-Once Flag Must Be Written Inside the Async Callback (2026-06-02)
**Learning**: Writing a "seen" flag to localStorage BEFORE a setTimeout (or any async callback) fires permanently marks the event as triggered before it happens. If the user navigates away during the delay, the milestone/modal/notification is permanently suppressed. Pattern: write the flag INSIDE the callback with a re-check guard: `setTimeout(() => { if (!localStorage.getItem(key)) { localStorage.setItem(key, "1"); show(); } })`. The re-check also prevents double-firing when the same component is mounted twice (e.g. layout + page both render the same component).
**Apply when**: any "show once" modal, tooltip, or notification triggered by a timer, scroll event, or async callback using localStorage as the deduplication mechanism.

## WSL Path Compatibility (2026-03-15)
**Learning**: When running across Windows + WSL2, tool configuration that references directories must include all 3 path formats: Windows (`D:\`), WSL-mount (`/mnt/d/`), native Linux (`/root/dev/`). Without all three, permission prompts re-appear depending on which environment the session runs from.
**Apply when**: Setting up any tool that uses directory allow-lists on a WSL2 machine.


## Rate Limiters Match Coarsely — Scope Them by What They Actually Protect (2026-03-15 → 2026-03-29)

**Learning**: A rate limiter selected by a coarse dimension polices traffic it was never meant to touch, and the damage is always downstream of the thing you were protecting. **By environment**: an E2E suite runs dozens of tests from a single IP in minutes and trivially exceeds production limits, so gate the middleware on an environment check (`NODE_ENV !== "test"`) — rate limiting earns its own unit tests rather than being exercised implicitly through E2E. **By URL prefix**: limiting `/api/auth/*` catches read-only GETs (session checks, user lists, config) alongside the mutations (login, signup, verify) the limit exists for, so a normal login+logout cycle exhausts the budget and subsequent GETs return 429, breaking unrelated UI. Limit by HTTP METHOD instead — POST/PUT/DELETE on auth paths get the strict limit, GET gets the default. The general form: name the abuse the limiter prevents, then match on the narrowest dimension that captures exactly that abuse. Whenever a new route lands under a rate-limited prefix, check whether it is read-only before letting the prefix rule apply to it.

**Apply when**: Adding rate limiting to any web server, especially one with an E2E suite; adding routes under an existing rate-limited prefix; auditing which endpoints a limiter actually covers.

## E2E Port Isolation from Dev Server (2026-03-15)
**Learning**: E2E test configs should use a dedicated test port constant or env var (e.g., `E2E_PORT`), never fall through to the dev server's `PORT`. With `reuseExistingServer: true`, tests silently connect to the running dev server instead of starting a fresh test server — causing mysterious failures from unrelated state.
**Apply when**: Configuring Playwright or similar E2E test runners in a project that also runs a dev server.

## Schema Enum Migration: Update All Raw SQL (2026-03-15)
**Learning**: After migrating string/text columns to database enums (pgEnum, MySQL ENUM, etc.), all raw SQL in test fixtures, E2E setup/cleanup, and seed scripts must be updated to use valid enum values. A value that worked with unconstrained text columns will throw constraint errors after migration.
**Apply when**: Converting text/varchar columns to enum types in any database.

## Test Factories Must Mirror DI Container (2026-03-15)
**Learning**: When adding a new service to the production DI container, always update test helper factories (e.g., `createTestApp`) to create and inject the same service. CI tests use the test factory, not the production startup — so a missing service causes `undefined` errors that only surface in CI, not local dev.
**Apply when**: Adding new services to a DI container in a project with separate test factory setup.

## Shared Package @/ Alias Breaks in Consumers (2026-03-19)
**Learning**: When app A's tsc processes files from a shared package via path mapping, the `@/` alias resolves using app A's tsconfig (not the shared package's). Fix: use relative imports in shared packages, never `@/` aliases.
**Apply when**: Creating shared packages in pnpm/npm workspaces with TypeScript path aliases.

## Cross-SPA Navigation Must Use window.location.href (2026-03-19)
**Learning**: In multi-SPA architectures (separate Vite builds per role), cross-role redirects (login, role-switch, route guards) must use `window.location.href`. Framework router `navigate()` only works within a single SPA boundary — it can't cross to a different Vite build.
**Apply when**: Building multi-SPA apps where different roles/portals are separate Vite builds.

## XHR withCredentials for Cookie-Based Auth (2026-03-19)
**Learning**: When using HttpOnly cookie sessions (Better Auth, etc.), XHR requests (file uploads) must set `xhr.withCredentials = true`. Without it, cookies aren't sent and the upload gets 401. `fetch` with `credentials: "include"` has the same requirement.
**Apply when**: Any file upload or XHR request in a cookie-based auth system.

## pnpm --filter: exec vs Script Name (2026-03-15)
**Learning**: `pnpm --filter <pkg> <arg>` treats `<arg>` as a package.json script name. To run a binary (tsx, tsc, vitest, etc.) scoped to a workspace package, use `pnpm --filter <pkg> exec <binary> <args>`. Without `exec`, pnpm fails with `ERR_PNPM_RECURSIVE_RUN_NO_SCRIPT`. This commonly bites CI workflows where commands are written as raw shell rather than package scripts.
**Apply when**: Running CLI tools scoped to a specific workspace package in a pnpm monorepo.

## Mobile Testing Progression and the Emulator Traps It Runs Into (2026-03-21)

**Learning**: Decide the mobile testing progression on day one: browser device-mode first (fastest loop), then emulators for the bulk of iteration velocity, then real-device APKs as the product matures, and only pursue app-store submission when the product is solid — store submissions carry real cost (developer accounts, review cycles, compliance), so readiness matters before that step. Two emulator traps bite hard in the middle stage. **Camera**: an Android emulator with `hw.camera.back=emulated` returns a valid MediaStream from `getUserMedia()` but produces a black/checkerboard feed with NO error thrown, so `catch`-based fallbacks never fire. Use `hw.camera.back=virtualscene` for testable video, and always ship manual entry alongside any camera viewfinder — a silent failure cannot be reliably detected at runtime. **AVD hygiene**: prefix AVDs with the project name (`<project>-<role>`) to avoid collisions across projects sharing one Android SDK, and make nuke/reset commands clean orphaned `.avd` data dirs under `ANDROID_AVD_HOME` — those are left behind when an emulator is running during `avdmanager delete`. Each project owns its own emulator config; no shared state.

**Apply when**: Setting up the testing strategy for any mobile-first or hybrid app; building camera features (QR, barcode, photo) tested on Android emulators; setting up emulator workflows in a multi-project environment.

## Layer AI Product Cost by Tier; Cache the Expensive Tier and Fire It Off the Response Path (2026-03-21 → 2026-03-29)

**Learning**: For any AI-powered product with high-frequency input, separate processing into layers with different cost profiles: **free capture → cheap classification → expensive generation only on-demand**. Most interactions touch only the cheap layers; the expensive layer fires only when the user explicitly asks. This is an architecture decision that IS a business decision — it is what makes the product viable for a solo founder. The runtime expression is **fire-and-forget**: capture must feel instant (<200ms), so heavy work (LLM classification, theme assignment, media pre-generation) fires AFTER the response is sent, never blocking it — don't await, use `promise.catch(() => {})`, and let the user see results on next view. The expensive tier then needs two disciplines of its own, learned from TTS, which in voice-first products is typically the single biggest scaling cost (often ~50% of total infra — model it separately and identify the tier boundary where it dominates). (1) **Persist on first generate**: store the rendered output (base64 in a column, or a jsonb map keyed by content) and serve from storage on every replay — never regenerate the same input twice. (2) **Stream when latency matters**: full synthesis adds 3–5s for long content; chunk streaming over a WebSocket with client-side scheduling gets first output playing in ~200–500ms. Persistence kills cost; streaming kills wait. Opt-in playback is additionally a UX win.

**Apply when**: Designing any AI-powered product with high input frequency and heavy processing — make the cost model, the persistence layer, and the streaming-vs-blocking call on day one.

## Offline-First Is Non-Negotiable for Capture Apps (2026-03-21)
**Learning**: When the core use case happens in a place with no internet (commute, underground, spotty signal), offline-first isn't a nice-to-have — it's the difference between the product working and not working. Auto-sync (not manual push) is correct because the whole point of a capture app is reducing cognitive load. Requiring the user to remember to sync defeats the purpose.
**Apply when**: If your primary use case happens offline, offline-first is table stakes.

## Trust Ladder Onboarding for Sensitive Features (2026-03-21)
**Learning**: When a product requires sensitive data (voice biometrics, diary-level thoughts), don't ask for everything upfront. Build a trust ladder: deliver core value first (basic features), then progressively unlock sensitive features (voice input → voice customization). The user should feel "of course I'll give you this" by the time you ask, not "why do you need this?"
**Apply when**: Any app requiring biometric or deeply personal data — design the onboarding progression.

## Modes as a Volume Dial, Not Separate Machines (2026-03-21)
**Learning**: When a product has multiple "modes" of interaction, check whether these are genuinely different processing pipelines or just different amounts of the same processing. Often all modes use the same engine — the mode is injected as context into one system prompt. This avoids maintaining N separate AI pipelines. The modes are a "volume dial" of AI involvement: from zero (quick action) to full (open dialogue with history).
**Apply when**: Prefer one adaptive system over many specialized systems when the variation is in degree, not kind.

## Provider Factory Consistency (2026-03-21)
**Learning**: When a codebase establishes a provider factory pattern (e.g., `createProvider<T>(envKey, registry, fallback)`), ALL environment-driven service selection should use it — including rate limit stores, cache backends, and queue implementations. Inconsistent ad-hoc if/else selection for one provider while others use the factory creates maintenance confusion and makes the pattern untrustworthy.
**Apply when**: Adding new environment-switchable services to a codebase that already has a factory pattern.

## AI Timestamps Are Unreliable (2026-03-26)
**Learning**: Do not add conventions requiring AI agents to prefix messages with wall-clock timestamps (e.g., `[HH:MM]`) or report elapsed times after tool calls. The agent's reported times are not accurate and add noise without value. If timing matters, instrument it at the tool/platform level, not in agent output formatting.
**Apply when**: Designing output formatting conventions for AI agents or reviewing proposals that include timestamp requirements.


## Real-Time WebSocket ≠ Push Notifications (2026-03-26)
**Learning**: WebSocket real-time (Ably, Pusher, Socket.io) and push notifications (FCM/APNs) solve different problems. WebSockets deliver updates while the app is open — they require an active connection. Push notifications reach users when the app is closed or backgrounded — they require platform-specific infrastructure (Firebase project, APNs key, server-side device token storage). For pilot/MVP launches with small user bases, WebSocket real-time is sufficient. Push notifications add significant infrastructure complexity (two vendor integrations, token lifecycle management, platform review requirements) and can be deferred to a post-launch sprint informed by real engagement data.
**Apply when**: Scoping real-time features for mobile apps. Don't conflate "real-time updates" with "push notifications" — decide which you actually need for launch.

## Configurable Paths via Resolution Chain (2026-03-15)
**Learning**: Never hardcode absolute paths in portable tools or skills. Use a resolution chain: (1) env var, (2) config file entry, (3) fallback default. This makes tools portable across machines and environments.
**Apply when**: Any tool or skill references a directory that varies by machine (repos, config dirs, data dirs).

## Android Edge-to-Edge Status Bar Overlap in Capacitor — Version-Dependent Fix (2026-03-22 → 2026-08-23)

**Learning**: Android enforces edge-to-edge rendering (API 35 by default, API 36 mandatory), so app content renders behind the status bar. **On Capacitor 8+, use the System Bars core plugin**, which manages insets through CSS `env(safe-area-inset-*)` — this is the current answer and the one to reach for on any new project. **On Capacitor 7**, the only working fix is `android: { adjustMarginsForEdgeToEdge: "force" }` in `capacitor.config.ts`; Cap 8 removed that config entirely. What does NOT work on Cap 7, and will waste time: `StatusBar.setOverlaysWebView({ overlay: false })` is silently ignored; CSS `env(safe-area-inset-top)` returns `0px` on Android WebView (only `safe-area-inset-bottom` works); `WindowCompat.setDecorFitsSystemWindows(window, true)` in MainActivity is overridden by Capacitor's BridgeActivity. Whichever version you are on, do NOT stack multiple fixes — each adds padding independently, producing a visible gap.

**Apply when**: Any Capacitor Android app targeting API 35+ where content overlaps the system status bar. Check the Capacitor major version first — the correct fix differs entirely between 7 and 8.

## Bidirectional Sync System Design (2026-03-28)
**Learning**: When designing any system that syncs files between a source-of-truth repo and deployed copies (skills, configs, knowledge), six rules must hold together:
1. **Three-way comparison** — source vs manifest vs deployed, so you can distinguish "source updated" (deploy it), "deployed updated" (reverse-sync it back), "both updated" (conflict, manual review), "neither" (skip). A two-way comparison can't tell which side moved without a baseline.
2. **Atomic edit-then-deploy** — direct source edits must immediately re-deploy to targets; otherwise a concurrent absorption run sees DIFFERS, treats the stale deployed copy as "newer," and silently reverts the source edit.
3. **Reverse-sync writes to source, never to deployed** — writing to deployed copies creates a permanent gap (deployed has more entries than source) that re-running cannot heal because trackers mark entries as already processed.
4. **Idempotent absorption tracker** — when absorbing entries from a source you don't own (append-only logs, learning files, changelogs), maintain a tracker (content hashes or titles) of already-processed entries so each run only evaluates new material.
5. **Self-flagging entries beat heuristic triage** — when a producing skill writes learnings, it should self-classify each as "promote-worthy" or "local-only" at write time; downstream consumers auto-promote without guessing.
6. **Don't duplicate the layer above** — forward-sync deploying conventions into a project workspace must check whether the global config layer already covers the convention before adding a project-level copy. Duplicating rules across layers creates drift.
**Apply when**: Designing or operating any bidirectional sync system (deploy + absorb) between a canonical repo and its consumers.

## Skills Own Their Dependencies and Their Discovery (2026-03-26)
**Learning**: A skill package must be self-contained in two senses. (1) **Dependencies**: any framework or reference doc the skill cites must live inside the skill's directory, not at repo root. Static reference docs in shared locations become stale orphans because the skill self-iterates but the orphan doesn't — co-location ensures everything evolves together. (2) **Discovery**: when a skill needs to be discoverable on fresh clone before global deployment, use a thin bootstrap file in the project's local skill directory (~3 lines) that points to the real skill file. Avoids symlinks (OS-dependent) and full duplication (drift risk).
**Apply when**: Structuring skill or plugin directories in any repo that is itself the source of truth for those skills.

## Firebase API Key Restriction for Public Repos (2026-03-29)
**Learning**: Firebase API keys are project identifiers (not secrets), but in public repos, ALWAYS restrict the key to the deployment domain via Google Cloud API Keys API. Add HTTP referrer restrictions (deployment domain + `localhost/*` + `127.0.0.1/*`). Security rules protect data integrity, but unrestricted keys let unauthorized apps consume quota or abuse Firebase resources from other origins.
**Apply when**: Setting up Firebase in any project, especially public repos or GitHub Pages sites.

## Silent Browser API Failures — Check Security Headers FIRST (2026-03-29)
**Learning**: When a browser API (`getUserMedia`, `Notification.requestPermission`, `navigator.geolocation`) fails silently — no prompt, no error UI, just a quiet `NotAllowedError` — the root cause is almost always a `Permissions-Policy` response header blocking it. `curl -sI <url> | grep -i permissions-policy` is step 0 before reading any client code. The HTML `capture` attribute on `<input type="file">` is also silently ignored when the policy blocks camera.
**Apply when**: Any browser API behaves as if the user denied permission but no prompt was ever shown.

## Bot and Crawler Protection Strategy (2026-03-29)
**Learning**: Block crawlers at every non-production tier and on every authenticated production surface — not just staging. Internal-only environments should layer all defenses (`robots.txt Disallow`, `X-Robots-Tag: noindex,nofollow` header, infrastructure-level auth gating, `noindex` meta). Customer-facing pre-prod that needs unauthenticated user access can only use app-level headers — infrastructure auth gating locks out the real users you're trying to test with. Production: allow crawling only on truly public pages (marketing, docs); every authenticated path gets `X-Robots-Tag: noindex` plus `Disallow` rules. A bot reaching an admin panel is a security incident, not an SEO miss. Platform-specific gating commands belong in a stack guide, not in this evergreen learning.
**Apply when**: Deploying any application. Decide upfront whether each environment needs unauthenticated end-user access — that decision dictates whether infrastructure gating or app-level headers is correct.

## Next.js 16 Process Renaming Breaks Zombie Kill Scripts (2026-03-29, literal last verified 2026-03-29)
**Learning**: ⚠ The literal process title below is a MIRROR of one vendor version's behavior at the date recorded, not a permanent fact — recheck it against the currently-installed version before trusting the exact string. As observed then: Next.js 16 renames its dev server process to `next-server (v16.x.x)` — a custom process title with no `node`, `next dev`, or project name in the command string. Standard pgrep patterns (`node.*next.*dev`, `node.*(next|playwright).*<project>`) miss it entirely. The process also auto-selects non-standard ports when the configured port is busy, so port-based `fuser -k` also misses it. The technique that survives a version bump even if the literal changes: kill/restart scripts should match whatever the CURRENT literal process title is (not assume `node`/`next dev`/the project name appear in it) and scope to the project by checking `/proc/$PID/cwd`, since a title can rename again in a future major version.
**Apply when**: Writing or updating restart/kill-zombie scripts for any Next.js 16+ project. The `/srs` skill templates need this pattern.

## Voice Clone Consent Flow Is a Legal Requirement (2026-03-29)
**Learning**: Voice biometrics are sensitive data under GDPR, UK DPA, and emerging US state laws. Before cloning a user's voice, present a dedicated consent screen with: what you collect (audio sample), how it's used (private TTS only), user rights (delete anytime), and third-party processing disclosure (name the provider). Use a checkbox-based explicit consent mechanism — implied consent from "tapping record" is insufficient.
**Apply when**: Any feature that processes voice biometrics — clone, voiceprint, speaker ID. Not needed for plain speech-to-text.

## Auth Library Territory: Don't Recreate, Don't Bypass (2026-03-29)
**Learning**: Any auth library that manages its own user/session/account tables owns identity, sessions, password hashing, and credential validation. Two anti-patterns to avoid together: (1) **never create a parallel "user-like" table** with overlapping fields (email, name, provider ID) — FK directly to the auth library's user table, extend via the library's own field-extension mechanism if supported, or use a thin profile table with only app-specific fields. (2) **never hand-craft sessions for mock/staging login** — use the library's own sign-in method and seed credentials via the library's own password-hash function. Unsigned cookies you craft by hand won't verify when the auth middleware checks them. If you're writing `response.cookies.set("session_token", ...)` in a mock auth route, STOP. The library is the single source of truth for identity AND for session shape.
**Apply when**: Designing schemas or building staging/dev mock login for any project using an auth library with its own user table.

## Cloud Services Must Have Local Dev Fallbacks (2026-03-29)
**Learning**: Every cloud service call (GCS, S3, email, push notifications) needs an env-gated local fallback. Write the local branch FIRST. Three tiers: local dev = filesystem/mock/console.log, staging = real cloud service, prod = real cloud service. Module-scope cloud client instantiation without an env check (`new Storage()`) crashes local dev immediately.
**Apply when**: File uploads, email sending, push notifications, or any external service integration. The local fallback is step 1, not step last.

## Centralize Drift-Prone Config — the Second Copy IS the Bug (2026-03-15 → 2026-07-09)

**Learning**: When the same configuration value — a schedule slot, a threshold, an enum→behaviour mapping, a tool convention — exists in more than one location, changing it means finding every copy and you WILL miss one. The miss is silent and downstream: a validator, a dashboard, or a doc keeps asserting the OLD value and emits a false alert or a wrong render that looks like a brand-new bug. The tell is chasing the identical literal from file A into B, C, D. **The moment you patch the same literal a SECOND time, stop and extract it** — one config file plus a small accessor exposing read helpers and a `verify` that asserts consistency (every reference resolves, no conflicts or duplicate roles), then wire ALL consumers: planners, validators, dashboards, AND docs. Run `verify` as a preflight so drift fails loudly instead of silently. The same rule governs config layering: when a tool supports both global and per-project configuration, put every standard setting in the global config and create per-project files only for genuine overrides — a full copy per project is the multi-copy bug wearing a directory structure. Corollary: separate the low-level "grid of every valid value" (changes rarely) from "which value is active/assigned now" (changes often); centralize the volatile assignment, keep the grid as its own constant, and have `verify` assert assignment ⊆ grid — retired values stay in the grid so old records still resolve but drop out of the active assignment. Stack-agnostic.

**Apply when**: Any project with scheduling, feature-flag, threshold, or slot surfaces; setting up project-level configuration for a tool that also has a global config. Trigger on the second edit of the same literal — that is the extraction signal.

## The Local Gate Replaces Remote CI Only When It Is Command-Identical and Clone-Clean (2026-04-03 → 2026-08-08)

**Learning**: Solo/small projects can legitimately move off auto-triggered remote CI to a manually-invoked local pipeline — auto-CI on every push burns minutes and adds noise during rapid WIP iteration. But the substitution only holds if the local gate carries three properties the remote one gave for free. (1) **Relocate before you retire**: read the remote pipeline's logs before deleting it — a red pipeline may be catching real defects rather than environment noise — and explicitly move each of its checks into the local ritual. Never delete a gate you have not first relocated. (2) **Command-identical, not correlating**: a lint plus a single-package `--noEmit` spot-check can pass while the production build fails, because the full workspace build's type-checker is stricter and test runners transpile without type-checking. The local verify must run the SAME commands the production artifact build runs — at minimum the formatter's check mode and the full workspace production build. A subset that merely correlates with the deploy gate will eventually green-light a defect. (3) **Clone-clean, not tree-clean**: a local pipeline validates the working tree, which silently contains generated and gitignored files (codegen, i18n, protobuf) a fresh clone lacks — so "all green locally" and "builds from clone" are different claims and only the second is what a collaborator or a deploy experiences. Add a scripted fresh `git clone` + install + build into a temp dir as a pipeline stage. The hosted CI vendor was never the point; the clean-room clone was. Corollary: E2E tests not wired into whichever gate actually runs are a safety net that never fires — add the tests and the wiring in the same change.

**Apply when**: Setting up CI for a solo/small project (default to manual trigger); auditing or defining a pre-commit/pre-push local gate; retiring a remote CI pipeline as "redundant"; declaring a repo "CI-clean" without a clean-clone build stage.

## GCP Artifact Registry Cleanup Policy Must Be Set Per-Repo (2026-04-16)
**Learning**: Artifact Registry cleanup policies are per-repository only — no project-level default. Every new Docker repo starts with NO cleanup policy. Old images accumulate silently and cost money. Standard policy: keep last 5 versions, delete rest (`{"action":{"type":"Keep"},"mostRecentVersions":{"keepCount":5}}` + `{"action":{"type":"Delete"},"condition":{"tagState":"ANY"}}`). Apply immediately on repo creation via `gcloud artifacts repositories set-cleanup-policies`.
**Apply when**: Any blueprint or deploy script that creates Artifact Registry repos for Cloud Run. Should be a checklist item in GCP deploy setup.

## A Success-Shaped Signal Is Not Proof — Assert the Property That Defines Success (2026-04-16 → 2026-08-30)

**Learning**: The most durable class of silent defect is one where every check passes because no check ever examined the thing that defines correctness. The signal that lies is always a cheap proxy: an exit status, a status code, "the run completed", "the directory exists", "the suite is green". Five shapes of the same failure: (1) **A pipeline can run cleanly and log success for weeks while producing zero output** — "last successful run" is necessary but insufficient; add a per-source "days since last new document / last produced output" metric, because silent discovery failure is a real failure mode no unit test or HTTP status check will catch. (2) **A test suite is green because the code path was conditionally empty in every environment that gated it** — no fixture seeded a row inside the query's window, so the `.map` over results never executed; the regression test that matters is the one that seeds a row INSIDE the window, since a test passing against empty state proves only the empty branch. (Its sibling defect: a raw SQL aggregate's TypeScript generic is a compile-time assertion with zero runtime force — ORMs apply driver-value mapping through column configuration only, so give every raw aggregate over a mapped column the column's mapper explicitly, never a bare generic.) (3) **A build step that discovers units by listing directories must assert the MARKER FILE that defines a valid unit** — a directory is cheap to create by accident and a half-built unit looks identical from outside. The tell is asymmetry: when one pass validates and another doesn't, the unvalidated pass defines what actually ships, silently, with a count that disagrees with the registry. Fix both loops to the same predicate and prefer failing loudly over skipping. (4) **A 200 in the wrong content type defeats every standard check** — an SPA fallback answering /robots.txt, /sitemap.xml, or /.well-known/* returns 200 text/html, nothing errors, the deploy reports success, monitoring sees healthy codes, and the crawler silently parses a web page as an empty rules file. Don't assert the route returns 200; assert the response is NOT HTML (or IS the expected type), per host, and serve such paths ahead of every redirect — a 301 into a catch-all is how the lie starts. (5) **The proxy can also lie by being EMPTY rather than green** — a join across two systems' identifier spaces (a local ledger against a platform's ids, an importer against source filenames, a metrics table against stored record ids) that fails to match anything returns a clean, plausible, SHRINKING answer indistinguishable from a legitimate empty result: no error, no exception, no empty-set warning. Worked instance: a namespace cutover changed a ledger's keys from platform ids to a composite handoff key (shaped like `<system>:<uuid>#<channel>`), so every newly-produced record was silently dropped by a join still written against the old namespace — the tracker kept reporting healthy while its dataset froze and shrank. The general rule: name the property that would be false if the system were broken, and assert THAT — never the proxy that merely correlates with it.

**Remedies for shape (5)**: before trusting a negative result from any cross-system join, prove a positive match CAN exist — assert that at least one row matches and fail loudly when zero do; a join that drops non-matching rows must count and report what it dropped, since "not our content" is a decision that needs a number attached; treat every join against a namespace that just changed (a cutover, a migration, a new writer) as broken until proven otherwise; and validate any alarm/detector meant to catch this against a known-positive sample, because a detector that cannot fire is worse than none — it reports safety.

**Apply when**: Designing observability for any source→sink pipeline; writing tests whose payload depends on time-windowed or conditional data; writing or reviewing any directory-enumerating build/packaging/deploy step; any server with an SPA fallback or hostname redirects; diagnosing any "it reports success but the effect is missing" fault; auditing any cross-system identifier join (ledger↔platform ids, importer↔filenames, metrics↔stored ids) after a cutover, migration, or new writer changes one side's key format.

## Single-Use Refresh Tokens Race Under Concurrent Processes (2026-04-26)
**Learning**: When several processes share one OAuth credential and the provider issues *single-use* (rotating) refresh tokens, simultaneous expiry triggers a race: each process refreshes with the same refresh token, the first wins, the rest get `invalid_grant` and crash. The durable client-side fix is a **cross-process lock on the credential write** — refresh under a lock, re-read fresh inside it, and preserve the existing refresh token if the provider's response omits one (RFC 6749 §6). A proactive scheduled-refresher is a lighter mitigation, but if you build one, mind three traps: (1) **scheduled, not polling** — sleep until `expiresAt - margin`, refresh once, recompute; (2) **the refresher races itself** — serialize bursts via non-blocking `flock -n`, exit on lock loss; (3) **clock-skew on suspend** — re-read `expiresAt` on every wake.
**Apply when**: Designing or reviewing any multi-process system that shares a rotating OAuth credential. Agent harnesses with concurrent subagent fan-out hit this exact race and now handle it internally with a cross-process credential lock — the lesson applies to your own SDK integrations, not to the harness.

## Domain, DNS, Email, and Hosting Are Four Independent Decisions — Decompose, Then Default (2026-04-22)

**Learning**: Domain registration, DNS hosting, email hosting, and application hosting are four independent choices. Users and agents instinctively bundle them — "we're deploying to cloud X, so we should buy their productivity suite", "the registrar offers email, so use theirs" — and for bootstrapped projects that bundling is almost always wrong. Cloud hosts don't care where DNS lives; they need records pointing at them. Email providers don't care where the domain is registered; they need MX/SPF/DKIM/DMARC records in whatever DNS you use. A per-user-per-month productivity suite is premature for one founder; forwarding plus a "Send As" identity via a free SMTP relay covers send and receive. Concrete upgrade triggers: (1) hiring, (2) needing shared inboxes like `support@`, (3) needing org-grade collaboration tooling. Separate concern that must never be conflated with any of the above: transactional email (signup, password reset) always needs its own provider regardless of inbox choice. Registrar transfers typically require ~60 days after registration, so a just-purchased domain must wait.

**Apply when**: Any "what should I use for X" question touching domains, DNS, email, or hosting. Decompose into the four layers and price each separately before recommending a bundle; challenge any "we need X because we're using Y" unless Y literally requires X. Deviate from the default only for a concrete reason (TLD unsupported, team already in an ecosystem, compliance requirement).

## AGENTS.md Is the Cross-Tool Standard; Per-Vendor Adapters Are a Soft Lock-In (2026-05-09)
**Learning**: When building tooling that targets multiple AI coding agents, the temptation is to build per-vendor adapters that emit each tool's specific config (a Claude-coupled rules file, a Cursor rules file, a Copilot instructions file, per-vendor command directories, etc.). This is a softer flavor of vendor lock-in: the tooling multiplies by the cardinality of the vendor matrix, drifts apart over time, and silently couples the build pipeline to whichever adapter manifests are maintained. The actual answer is **`AGENTS.md`** — an open standard stewarded by the Agentic AI Foundation under the Linux Foundation, adopted by tens of thousands of open-source projects. Plain markdown, no required schema, no YAML frontmatter. Most agent CLIs read it natively. For agents that don't yet read `AGENTS.md` natively, a thin bootstrap (a one-line `@AGENTS.md` import in the vendor's expected file, or a symlink) is enough — zero behavior change, no per-vendor build path. One source, one universal output, plus a tiny per-tool bootstrap only where the vendor genuinely cannot read AGENTS.md.
**Apply when**: Designing or evaluating tooling that produces config for multiple coding agents. **Default to AGENTS.md** as the single output. **Reject per-vendor adapters** unless a vendor genuinely cannot read AGENTS.md. Keep vendor-specific surfaces (permissions, MCP, hooks) as opt-in helpers, not in the main build. **Anti-pattern**: a build pipeline with one target per vendor (`build vendor-a`, `build vendor-b`, …) — that's the lock-in trap with extra steps.

## Memory-Write Discipline Is Required For Any AGENTS.md Divorce (2026-05-09)
**Learning**: Divorcing a vendor-specific rules file from `AGENTS.md` (whether via symlink or via a 1-line `@AGENTS.md` import) is fragile because most agent harnesses provide memory-append paths that bypass the abstraction — keyboard shortcuts, slash commands, and init/regen tools that write directly to the vendor file with no target override and no awareness of imports/symlinks. There is typically no settings option to redirect these writes. Without an explicit discipline rule in AGENTS.md, repeated memory-append invocations slowly pollute either the thin pointer file (with `@-import`) or the rules file itself (with symlink — since the write transparently lands in AGENTS.md). Either way, the cosmetic divorce erodes back into the same vendor-coupled blob over time. The fix is *not* technical — it's a codified rule + behavior change.
**Apply when**: Setting up an AGENTS.md divorce in any project. Always include a "Memory write discipline" section in AGENTS.md stating: (1) AGENTS.md is rules, not storage; (2) memory storage lives in `memory/` (always-on) or `<sphere>/memory/` (sphere-scoped); (3) users must NOT use the harness's direct memory-append paths — instead, ask the agent to "remember X" so it saves via auto-memory (which lands in `memory/`, divorce-safe). Bonus: bake a janitor scan into the pre-commit ritual that walks every vendor rules file in the repo and flags any content beyond the bare `@AGENTS.md` line / symlink target — catches the bypass before commit.

## Multi-Sphere Vaults: Per-Sphere AGENTS.md + Per-Sphere memory/ Makes Focus Convention Structural (2026-05-09)
**Learning**: Multi-domain vaults (one repo containing many semi-independent peer subdirs) benefit from giving each sphere its own `AGENTS.md` + its own `memory/MEMORY.md` index, with sphere-scoped memory files inside the sphere's `memory/` dir (sphere prefix dropped from filenames since the path encodes sphere). The root `memory/MEMORY.md` becomes a thin index: always-on entries (load every conversation) + a pointer table per sphere ("for sphere-X memory, see `<sphere-x>/memory/MEMORY.md`"). Sphere AGENTS.md files reference their local `memory/MEMORY.md`. The win: the **focus convention becomes structural rather than procedural** — agents reading `<sphere>/AGENTS.md` literally only see that sphere's memory; off-sphere entries are physically out of sight, not just behind a "don't read this" rule. Bonus: `git add <sphere>/` captures everything sphere-related (rules, memory, content) in one diff scope.
**Apply when**: Divorcing a multi-sphere vault (or any repo with peer-equal subdirs that are semi-independent domains). Single-domain projects don't need this — a flat root-level `AGENTS.md` + root `memory/` is fine. The pattern only earns its keep when the project has 3+ peer domains AND memory accumulates per-domain. For harnesses with auto-loading subdir rules files (e.g., a one-line `@AGENTS.md` pointer in each sphere's vendor file), the cross-tool divorce composes cleanly with the harness's existing auto-load behavior.

## Evaluating New Model Classes for a Serving Gateway — Probe Hardware First, Slot as a Tier (2026-06-13)

## Background Orchestrations Die With the Host Session — Design for Resume-by-ID + Durable Incremental Writes (2026-06-28)
**Learning**: A long-running background orchestration (a multi-agent workflow, an async sub-agent, any detached job spawned inside an interactive agent harness) is bound to the host process/session. When that session disconnects or the process exits — a laptop sleeping, a mobile client backgrounding, a tab closing — in-flight work stops with no completion record, even though the harness reported it as "launched." Two properties decide whether this is a setback or a catastrophe: (1) whether each unit of work writes its output to durable storage *as it finishes* (so partial progress survives), and (2) whether the orchestration is *resumable by id* with already-completed steps returning cached results. Designs that buffer all output until a final flush lose everything on disconnect; designs where each step commits its artifact immediately lose only the in-flight step, and a resume re-runs from the first incomplete step. The cost of a disconnect then becomes time, never correctness.
**Apply when**: Launching long background workflows or async agents from a disconnect-prone session (mobile, web, anything not a stable terminal), or spawning any agent for data generation / bulk file creation expected to run more than a few minutes. Prefer orchestration that journals step results and resumes by run-id; have each step write durable artifacts incrementally rather than at the end; and on a "no completion record" notice, inspect what landed on disk before relaunching — then resume rather than restart. Durable incremental writes do not happen by default in a delegated agent — **instruct it explicitly in its prompt**: "Write incrementally — append every 20-50 items. Do NOT buffer everything and write at the end." The pattern is generate batch → append → generate next batch → append.

## Public Static API From Private Source — Split Private Builder + Public Mirror, One-Way Deploy-Key Sync (2026-06-28)
**Learning**: To expose a public, keyless, CDN-served static-data API while keeping the build logic, fallback strategy, and raw inputs private, one repo cannot do it — public static hosts that serve straight from a VCS only serve *public* repositories, so a private repo has no public path. The pattern is two repos: a **private source repo** (builder, source registry, raw landing zone, automation) and a **public mirror repo** holding only the consumer surface (the data, its schemas, a discovery catalog, the long-form archive). The build runs in private and syncs the allow-listed public paths into the mirror over a **write-scoped deploy key**. The path allow-list *is* the security boundary — it must be an explicit include-list in one script, never an exclude-list, so a new private artifact is private by default. Provenance (which upstream sources contributed) stays public because it is what makes the data trustworthy and is often required by source-attribution terms; only the *method* is hidden.
**Apply when**: You want a public dataset/API but must keep build internals, competitive logic, or raw third-party payloads private. Use a private builder + public mirror, sync one-way via a write-scoped deploy key for the high-frequency path and a separate narrowly-scoped token only where an API (e.g. release uploads) genuinely needs it, and make the public surface an explicit include-list in one script that doubles as the audited public/private boundary.

## Delimited Feeds With Free-Text Columns — Index Stable Fields From the End, Not the Front (2026-06-28)
**Learning**: When parsing a delimited feed (CSV/TSV/SDMX) where a free-text column (a title, description, or label) can contain the delimiter and the upstream does not reliably quote it, front-indexing the value/timestamp columns silently corrupts or drops rows the moment a delimiter appears in that free-text field (a label rendered "City, Country" injects an extra separator, shifting every subsequent front-indexed column by one). The robust technique is to address the stable trailing columns (the value, the period, status flags) by **offset from the END of the row**, and the stable leading keys (before the free-text field) by offset from the front. A delimiter injected into the middle field then shifts only the fields between the two anchors — never the value or date. Pair this with a length check that *tolerates extra* fields (count >= header length) rather than rejecting rows whose count differs, since the naive "field count must equal header" guard is exactly what drops the injected-delimiter rows.
**Apply when**: Parsing any externally-sourced delimited data where a descriptive column may contain the delimiter and quoting is unreliable. Anchor leading keys from the front and trailing values from the end, derive the trailing offsets from the header so the parse also survives column-order changes, and never use exact-field-count as a row-validity gate when free-text columns are present.

## Time-Series File Archives — Partition by Effective Date + Dedupe, Not Ingest Date (2026-06-28)
**Learning**: A file-based, append-only time-series archive (one shard per day in a VCS or object store, rebuilt on a schedule) duplicates data badly if it partitions by *ingest/build date* while each record carries its own *effective date*. Slow-moving or carried-forward values (a weekend rate, a policy figure unchanged for a year) get re-emitted into every build's partition, so a downstream "all values for entity X" query returns N copies per effective date and the cold-tier roll-up accumulates duplicates without bound. The fix is to partition by each record's **own effective date** and make each partition file idempotent: on write, merge with what is there, dedupe on the natural key (date, entity, field) with the freshest build winning, and emit sorted. Then a value re-observed across many runs is recorded exactly once, an unchanged day rewrites byte-identical content (so the VCS sees no diff), and re-runs are safe. The row *count* stays bounded by distinct observations, not by the number of builds — which is the property to assert in a test.
**Apply when**: Building any file/VCS-based time-series archive that rebuilds on a schedule and whose records have an effective date distinct from the ingest date. Partition by effective date, dedupe on the natural key per partition, and verify idempotency by asserting the total row count is stable across repeated rebuilds.

## Standing Up a Social Media-Publishing Integration — Three Gates, In Order (2026-07-05 → 2026-07-09)

**Learning**: A publishing integration against a large social platform clears three gates in sequence, and each one fails in a way that looks like a different problem. **(1) The login path, chosen by footprint.** When a brand has no presence on the parent platform, do NOT stand up a hidden/empty parent Page just to reach the child network. Major platforms expose two paths: a parent-login path where a Page access token reaches the child account through a linked Page, and a direct child-login path where the professional (Business/Creator) account authenticates on its own host with a user token and no parent presence anywhere. The container→poll→publish flow and the insights/comments endpoints are IDENTICAL on both hosts because they are relative to the child account id — converting an existing adapter is mostly host + token-source changes. The decisive trade-off is token lifetime: the direct path's user token typically expires (e.g. 60 days) and needs a scheduled refresh job, whereas a classic parent Page token can be permanent. Decide by whether the brand should have any parent-platform footprint at all, and pair the direct path with a refresh job before building. **(2) The app's authorization state, not your request shape.** After a textbook-perfect OAuth — token issued, all scopes granted — every call can still fail with one blanket error on every endpoint including identity reads. This is not a method, endpoint, version, host, or HTTP-client bug: while a platform app sits in **Development mode**, its API only serves accounts holding a **role** on the app. The fix is a dashboard step, not code: add the account under App roles → testers and accept the invite from inside the platform's own app; every call works instantly, no App Review, no Live mode. The generalizable tell: a UNIFORM error across endpoints a valid token should reach means "this account isn't authorized on this app yet", not "this call is malformed". Skip the misleading diagnoses that cost hours — identity alias vs numeric id, API version, personal-vs-professional account type, sandbox mode. App Review is about reaching OTHER people's accounts; publishing to an owned account needs only the role. **(3) Burst throttling that is media-type-specific and self-renewing.** Such APIs throttle rapid-fire creation in a way that hits multi-item posts far harder than single-item ones, because a multi-item post fires many calls in a 1–2s burst (one container-create per child, plus parent create and publish) while a single post fires one. It reads like an account-wide block but isn't: quota is nowhere near its limit, the token is valid, and other post types on the same account succeed — so ALWAYS split failures by media type, and check the platform's own quota endpoint, before concluding the integration is blocked. Three fixes compound: sleep a few seconds between per-child container creates; don't poll child containers that are ready instantly (per-child status GETs add burst that helps trip the throttle — poll only the parent and genuinely-async video containers); and mind the trap — such a lockout can last ~24h and **reset on every attempt made during it**, so a retry cron or a manual "let me just try again" restarts the clock and the block never clears. Honor the provider's transient flag: a non-transient error is dropped after ONE attempt, never retried, and a windowed publisher needs a media-type-specific cooldown that holds the offending type while letting others flow.

**Apply when**: Standing up, migrating, or debugging any social/media publishing integration. Choose the login path before building the adapter; check app mode and account role before debugging request shape; design per-type cooldowns and a no-retry rule for non-transient blocks before the first burst failure, not after a multi-day outage.

## What Lives in One Consumer of Shared Infra Reaches No Other — Promote It (2026-07-14 → 2026-08-23)

**Learning**: When several projects or users each integrate the same shared internal service or tooling repo, each typically hand-rolls its own client or local config. Anything learned there stays there, in both directions. **The defect direction**: a gotcha discovered and fixed in one consumer — an endpoint needing a specific header+body shape, a silent failure mode — lives only in that project's fix log. ## Mirrors of External State Must Carry Provenance (2026-07-26 → 2026-08-31)

**Learning**: A value stored in a repo that describes something OUTSIDE it — a deployed image tag, a vendor's hardware class, a price, an FX rate, "what artifacts exist on disk" — is a MIRROR, not a fact. With no record of when it was last confirmed, a stale mirror is indistinguishable from a correct one, so confidence stays high while truth drifts. Three separate wrong conclusions in one session traced to this: a config naming a deployed version two minors behind reality, a plan citing an external discussion thread nobody had opened (it was about something else), and an analysis of a 0%-failure bucket that was really failures being overwritten in place by the producer's retry. What compounds it: a test asserting a mirrored value's CONTENT turns staleness into green CI — a test hardcoding the same literal as the config it checks agrees with that config forever and actively endorses the drift.

**Correcting the mirror does not correct what was DERIVED from it.** A provenance entry guards a mirrored VALUE; it cannot guard a value merely derived from one, because that dependency usually lives in prose and is invisible to any mechanism — a worked instance: a config correctly recorded that a piece of vendor hardware had been wrong for months and was fixed against a billing ledger, while several code comments elsewhere still asserted the old hardware as present fact, one of them justifying a request-size ceiling with headroom the real hardware does not have. A justification written in a comment is itself a claim subject to the same rot as the value it justifies — "X is well beyond what we need" asserts a fact about X, and nobody audits justifications the way they audit values.

**A credential's, API's, or schema's set of CONSUMERS is not discoverable from the repository that issues it.** Thoroughness inside a boundary is indistinguishable from correctness until you leave it — a worked instance: a full trace of every secret's consumers within one service's own codebase was complete and still wrong, because the decisive fact (one leaked value was actually an inbound allowlist covering three downstream services, with the fallback everyone assumed covered it already retired weeks earlier) lived in a different repository's rules file and a third repository's migration note.

**A rehearsal against the real thing is how you leave the boundary, and its redundancy is unfalsifiable in advance** — which is exactly why it gets skipped. A transport passed a large test suite and multiple adversarial reviews against a faithful fake server; a single run against the real one found that key-scoping advice in the product's own output was false, because the fake could not model path reach and so no review of the fake could have found it. Anything whose dependants live elsewhere — credentials, published interfaces, shared identifiers, config another service reads — cannot be audited from home.

**A confidence LADDER beats a boolean `verified` flag.** Record how a claim about external reality is known: asserted, spec-conformant, probed against the real system, or observed live. Each rung carries information a single true/false throws away, and the rungs tell the next reader what would raise confidence.

**Mitigations, in leverage order**: (1) give every mirrored value an entry recording what it mirrors, where the truth lives, HOW to re-check it, and when it was last confirmed, plus a test that FAILS once overdue — the test failing with no code change is the feature; (2) assert a mirror's SHAPE or that it matches its declared source, never its literal content; (3) treat a citation as a promise until fetched — quote the source's title or a line from it, never a bare issue number; (4) before interpreting a population of artifacts, find the producer's WRITE PATH — if it can overwrite, retry, or clean up in place, the survivors are a filtered sample and any rate computed from them is meaningless, with a 0% or 100% bucket as the tell; (5) before believing a metric correlates with some dimension of the input, re-measure the SAME artifact along that dimension — if the number does not move, the metric is clean and the effect is real or selection; (6) when you correct a mirrored value, grep for the OLD value AND the reasoning it supported, not just the field you fixed — anything justified by the old number is now unjustified even if it is still right, and "still right by luck" is a different state from "still right by derivation"; (7) prefer recording that a rehearsal against the real system happened over trusting fixture coverage alone, since a fixture can only be wrong in ways nobody thought to model.

**Apply when**: storing any externally-owned value in config (deployed versions, vendor hardware, pricing, rates); writing a test that touches such a value; citing an external issue/discussion in a plan; computing failure rates or comparisons over artifacts a pipeline produced; tracing a credential's or schema's blast radius (assume consumers exist outside your own repository); deciding whether a fixture-only test suite is sufficient before a launch or cutover.

## Capturing a Real Browser Session Needs a Full Stack and Frame-Level Verification (2026-08-15 → 2026-08-27)

**Learning**: Recording or live-sharing a browser — for a compliance video, a reviewer demo, submission evidence, or a customer-facing repro — fails in layers, each of which is silent. **The display stack**: capturing a specific window by X11 window-id on a Wayland-backed display never sees native popups (a `<select>` option list, a context menu) at all — they render as a separate override-redirect window outside that window's composited buffer, and x11vnc refuses a Wayland display outright. Switching to a genuine `Xvfb :N` makes the popup's WINDOW visible but not its CONTENT — the browser auto-disables GPU compositing on a GPU-less Xvfb and its software presenter silently fails to paint override-redirect surfaces, producing a correctly-sized BLANK popup. The third and actual fix is a trivial window manager (e.g. `fluxbox`) running alongside Xvfb, because popup handling depends on WM semantics even for windows nominally exempt from them. Build the whole stack (Xvfb + WM + VNC + plain x11grab) up front rather than discovering each missing layer from a symptom. **The launch**: a GUI app started from a background shell reports exit 0 while creating no window — its singleton mechanism forwards the open-URL request over IPC to an existing instance holding the same profile lock, on the OLD display; a separate run once produced zero renderer processes with no log error at all. Always verify the actual window exists (window search, renderer-process count for that profile, or a screenshot of the target display) before proceeding; never trust the launcher's exit code. **The frame**: any capture leaving the team must show the product and nothing else. Launching a browser as root silently adds a sandbox-disabling flag and the browser paints an "unsupported command-line flag" banner directly above the thing being judged. A capture API that records only the page viewport excludes it by luck, not design — a window grab, an OS recorder, or a different library lands it in the file. Suppress automation infobars (`--disable-infobars`, `--test-type`, or run non-root), avoid recording browser chrome, close notification/consent overlays first — then extract a frame from the finished file and LOOK at it. "This API records the page, not the window" is a claim about a library, the same class of assumption that fails everywhere else. **The profile**: a browser profile silently encodes the environment it was created in, and moving it between environments fails in ways that are quiet and sometimes unrecoverable. A profile created under a keyring-backed desktop session and then relocated to a bare Xvfb display for recording can no longer decrypt its cookie store — every login is lost, and it does NOT recover when the profile is moved back to the original display. Separately, a profile inherited from another host refuses to launch at all when its singleton lock/socket names a process on a display or machine that no longer exists — the browser is correctly refusing to risk corruption, not malfunctioning; deleting the stale singleton lock/cookie/socket files (safe: they name a process, not your data) is the fix. Neither failure announces itself as "you moved the profile" — one presents as mysteriously signed-out, the other as a launch that produces no window with only a line buried in the log.

**Apply when**: Recording or sharing a live view of a human operating a real browser (compliance/audit videos, captcha/2FA demos); launching any GUI app from a background shell, especially against a possibly-locked profile or a fresh display; producing any browser recording or screenshot for an audience outside the team; relocating an authenticated browser profile between machines, displays, or environments — treat that as destructive unless proven otherwise, and log in inside the display you intend to use rather than moving a profile into it afterward. The prompt: "if a reviewer paused on any frame, would they see only the product?"

## A Collapsing Formatter Can Eat Your Regression Test's Control (2026-08-15)

**Learning**: When a regression test asserts on output DOWNSTREAM of a formatting layer that deduplicates or collapses repeats ("2 × <line>" roll-ups, uniq filters, pretty-printers), the layer can absorb exactly the defect the test was written to detect — the break-the-check control passes with the guard disabled, and the test proves nothing. Witnessed live: a digest's repeat-collapse merged two identical stale rows into one line, so a count-the-lines assertion could not see the duplication it targeted. Invert the assertion to the formatter's own tell (the "N ×" multiplier's absence), or assert upstream of the collapsing layer. Always run the disabled-guard control and be suspicious when it passes on the first try. ## Third-Party Embeds Can Be Owner-Gated Per-Item — Bisect by Item Before Blaming Your Code (2026-06-02)
**Learning**: A third-party media embed (video, map, document viewer) that renders "unavailable" inside your iframe while the same item works at the provider's own URL is an item-level or origin-level *permission*, not a CSP, browser, or code fault — and the tell is that a different item from a different owner embeds fine on the identical page. Provider-side gates are per-item and largely invisible to the embedder: embedding disabled by the owner, unlisted/private status, audience/age designations that silently strip embed features, region blocks, and origin gates that behave differently on `http://localhost` than on an HTTPS origin. Diagnose in this order, all free: (1) open the item at the provider's own URL on the same device — if it works there, your code is not the cause; (2) swap in a known-good item from a different owner — if that works, the gate is item-level and unfixable from your side; (3) only then test an HTTPS origin (a tunnel to localhost is enough) to separate an origin gate from an item gate. Do NOT invent a provider setting to explain the behaviour — record what you observed and what you swapped, since embedders cannot see the owner's configuration.
**Apply when**: Any third-party embed that shows "unavailable" in an iframe but works at the provider's own URL. Bisect by item and by origin before touching CSP, sandbox attributes, or player parameters.

## A Deterministic Guard That Only Speaks One Language Silently Stops Guarding (2026-08-15)
**Learning**: A regex/keyword safety net over user-generated text (force-review triggers, abuse filters, escalation nets) written in English-only stops guarding the moment a real audience arrives — and it fails silent: the guarded system keeps running, the net keeps passing everything, and the miss surfaces as a public incident, not an error. The failure compounds with an LLM judge in the same lane: a polite factual correction ("Eso no es correcto") reads as neither complaint nor question to the model, so BOTH nets pass it. Fixes: (1) name the semantic category explicitly in the LLM's instructions ("claims the post is wrong/mislabeled/AI-generated/fake, in any language") — the model handles languages the regex will never list; (2) extend the deterministic net with the audiences' actual languages, accepting over-match (cost: one human glance) over miss (cost: the brand autonomously defending a wrong post); (3) mind JS \b: it is ASCII-word-based, so accented phrases ("não é") need substring matching, not word boundaries. Test both directions: claims force review AND plain praise in the same languages does not.
**Apply when**: Any deterministic text-trigger list over user content in a product with a non-English (or even potentially non-English) audience; any auto-send/auto-action lane gated by keyword nets.

## A Uniqueness Check Is Only as Global as Its Lock Key (2026-08-15)
**Learning**: A check-then-insert guarded by an application lock prevents only the races the LOCK KEY covers — a per-tenant lock closes same-tenant races and is invisible to cross-tenant ones, which are precisely the ones a multi-tenant product must fear (two customers claiming the same external account). The only guard that holds at every scope is the database constraint (unique index); the app-level check remains as the friendly-error path. The second-order trap: the comment above the lock described the covered race with complete accuracy — and correct prose above an insufficient guard reads as a settled question, which is exactly why nobody looked further. When auditing concurrency guards, ask "what is the lock KEYED on?" and enumerate the actors who don't share that key; also expect fixtures to break honestly when the constraint lands (shared literal ids across test tenants are the index working).
**Apply when**: Any check-then-act on a uniqueness invariant in a multi-tenant system; any review of code whose safety comment reads convincingly.

## A Claim Hardens Into a Premise the Moment It Is Written Down — Relaying Is Asserting (2026-08-16 → 2026-09-04)

**Learning**: An API scope/endpoint name that follows a vendor's real naming style (matching the shape of genuine neighboring names) reads as obviously real and gets passed between sessions, briefs and application drafts as fact — every downstream reader inherits it as a premise, planning retirements and adapter work against an API that does not exist. The whole plan survived several capable reviewers because each verified everything DOWNSTREAM of the name (sequencing gates, demand evidence, structural claims) while the name itself entered unverified upstream. This is the special case of a general law: **you verify claims you intend to ACT on and merely repeat the ones you intend to pass along — but relaying a claim IS asserting it, because the reader on the other end cannot tell which party checked it.** A wrong item in a handover costs exactly what a wrong item in a document costs; that you didn't personally originate it buys the reader nothing. This binds hardest on summaries, because a summary is precisely where unchecked items travel — compressed, confident-sounding, stripped of whatever hedges the original source carried.

**Remedies**: before any external API name enters ANY document — a brief, a design doc, an application draft — check it against the vendor's own catalogue (scopes reference, product list, docs URL resolving), and record the check; absence from public docs does not disprove a closed programme, so the follow-up is a written vendor question, not an assumption in either direction. More generally: when passing on anything from a subagent, a peer session, or a document, either verify it yourself or attribute it explicitly as unverified — never let the act of relaying imply the act of checking.

**Apply when**: Writing anything that names a third-party scope, endpoint, or product; inheriting a brief that names one; reviewing plans whose feasibility rests on a named external capability; and more broadly, any time you are about to pass on a claim from a subagent, a peer session, or a document — verify it or flag it as unverified, especially inside a summary. Cross-reference: `purge-learnings.md`'s "A Proposal Invents Its Own Provenance" is the same law applied inward — a proposal citing prior art that doesn't grep to a real file is a claim about your own knowledge base hardening unverified, rather than a claim about the outside world. Do NOT merge this with "Approval Does Not Travel Between Sessions" — that entry is about authorization scope between sessions, a different axis from whether a factual claim was checked.

## Approval Does Not Travel Between Sessions (2026-08-16)

**Learning**: In multi-agent work, a user's approval is scoped to the session that asked. Relaying "the user said yes" from one session to another as authorization is permission laundering in its politest form: a decision made in one context becomes a licence in another, and neither side ever sees the seam. The benign version (both sessions independently got the same answer) is indistinguishable at relay time from the harmful one (the answer covered different work than the receiver thinks). Rule: each session asks its own user question for its own decisions; a relayed approval is INFORMATION ("expect them to say yes"), never AUTHORIZATION. The receiving side's correct behaviour is to decline to act on the relay and close the decision in its own session.

**Apply when**: Any cross-session/agent handoff involving a pending user decision; writing coordination messages that mention what the user approved.

## The Authoritative Row and the Data-Bearing Row Can Be Different Rows (2026-08-19)

**Learning**: Before deleting a duplicate record, check what data exists ONLY on the row you are about to delete — the row that looks authoritative by every obvious signal (real lineage, correct provenance, the write you trust) may not be the row holding the asset pointers or media references. Evidence: fifteen duplicate-record groups in a production ledger, each representing one real item recorded twice — one row written by the current system with true lineage, one row imported by a legacy pipeline. The obvious cleanup is keep-the-lineage, drop-the-import. But the import rows held ALL fifteen thumbnails and the lineage rows held ZERO. The delete would have traded a duplicate listing for fifteen blank tiles, silently — nothing errors, and the surviving row still looks correct by every field you would think to inspect. This generalises because duplicates arise from two different writers, and different writers populate different columns; the split is the normal case, not the exception. The rule: diff the columns across the group and ask "what is non-null ONLY on the row I am dropping?" Prefer an order that heals first — let the repair/refresh path restore what the duplicate uniquely holds, VERIFY it landed, then delete. Delete-first is unrecoverable, and the verification step is the one people skip because the repair "should" have worked.

**Apply when**: Writing or reviewing any de-duplication cleanup, data migration that collapses records, or "tidy up the duplicates" task.

## A Guard Enforced In Every Caller Is a Convention, Not a Property (2026-08-19)

**Learning**: When a safety rule (a cutover flag, a kill switch, a permission check) is enforced by every CALLER rather than at the seam those callers share, the guarantee is "every author remembered" — that is a convention, not a property, and the exception is always a manual, off-schedule tool nobody thinks of as part of the system. Evidence: during one migration cutover, two independent legacy codebases were audited for reachable native-publishing paths. In both, every scheduled/cron path was correctly gated. In both, exactly one manual script — written for a one-off demo or audit recording, not on any schedule, called by nothing — reached a live publish API with no guard at all. One of them additionally read its input straight from a still-populated pending queue. The adapters themselves carried no awareness of the rule in either codebase. Scheduled paths get audited because they run on their own; manual tools are invisible to that audit precisely because nothing triggers them — until a human does, usually during exactly the kind of demo or debugging session that a migration creates. The rule: put the guard at the narrowest seam every path crosses — the function that makes the network write, not the CLI entry point, so a future direct import is covered too. Then verify by EXECUTION, not compilation: import the module with the flag set and call the guarded function, expecting the refusal — a syntax/compile check proves nothing about whether an import resolves or a guard fires. Where the seam cannot hold the guard, add a mechanical check (grep for files calling the write function that do NOT import the guard module) so the convention becomes a test.

**Apply when**: Auditing a system for reachable paths during a migration or cutover; adding a kill switch or feature flag that must hold everywhere; reviewing "we gated all the publish paths" claims.

## A Borrowed Terminal State Carries Semantics You Did Not Ask For (2026-08-19)

**Learning**: When you need a record to stop being processed, reaching for an existing terminal status because it happens to remove the row from a query is how you inherit that status's OTHER meanings — and the one you did not read is usually the one that fires. Evidence, three instances in a single evening across two engineers on one codebase: (1) a de-duplication guard scoped to one key was assumed to mean "one real object has one key" — it did not, the same real object could arrive under a second key from a different import path, so the guard silently admitted duplicates; (2) a never-repeat guard was wired into a new intake path by reusing an existing helper that wrote its entries as PERMANENT, correct for its original caller — on the new path it would have permanently banned every item on first sight, exhausting a rotating content pool within two weeks, converting a duplicate-content bug into a total outage; (3) a record whose external identifier had become unresolvable needed to stop being retried forever — the obvious fix set its status to "failed", the only terminal state that removed it from the sweep's queries, but the publish path atomically RE-CLAIMS any record in "failed" state with an expired lease, so "failed" did not mean "stop", it meant "claim me and retry"; ten records, all verified genuinely live on the platform, would have been re-published. Each was invisible until someone read what the existing path actually DOES rather than what its name implies, and in each case the reviewer who caught it was not the author. The rule: before reusing a status, helper or code path for a new purpose, enumerate every consumer that reads it and what each infers. When no existing state means what you need, add one (a dedicated nullable column costs a migration and is honest) rather than overloading a state that means something adjacent. And prefer a reviewer who did not write it — all three were caught by the other person.

**Apply when**: Reusing an existing status/enum value for a new situation; wiring an existing guard or helper into a new call path; any change whose implementation is "set it to the state that makes it disappear from the query".

## Reverting a File That Swept In Someone Else's Work Destroys Their Working Copy Too (2026-08-23)

**Learning**: Reverting a file to undo work you accidentally captured in your own commit also destroys the original author's UNCOMMITTED working copy of that work — not just the git history. The instinct is "I only rewrote history, their disk is untouched," and that instinct is wrong in exactly the one situation where you would ever perform this revert. The mechanism: their edits were uncommitted, sitting only in the shared working tree. A whole-file `git add` captured them, and the resulting commit made the working tree and HEAD identical for that file. A later revert therefore moves both — there is no longer any divergence for the working copy to preserve. The author's diff on that file comes back empty, and the code exists in neither HEAD nor on disk. Observed in a multi-agent setting: one writer's whole-file add swept another writer's in-flight feature into an unrelated commit; the revert was correct on the information available, but the commit message claimed the other party's work was "untouched on disk, still uncommitted" — it was not. A useful corollary on scope: only what was committed-then-reverted is destroyed — files carrying the same feature that were never committed were never revertable and survive untouched, so before rebuilding, search the tree for the feature's identifiers to establish what actually died, since the initial assumption of damage is often larger than reality. The rule: before reverting a file that swept in someone else's work, confirm with them — or at minimum tell them afterward that their working copy is gone too, because they will assume it isn't and may not check for hours. Prefer removing your own hunks over reverting the whole file. And when reporting the revert, state what you verified rather than what you assume — "their copy is untouched" is a claim about someone else's disk that costs one command to check and misleads badly when wrong.

**Apply when**: Reverting or amending any commit that captured another party's uncommitted work; writing the message for such a revert; assessing how much was lost after an accidental sweep; any multi-agent or shared-workspace setup where several writers share one working tree.

## Prove a Compile-Time Guarantee by Breaking It, Not by Asserting It (2026-08-08 → 2026-09-01)

**Learning**: A refactor whose value is "this bug class is now a compile error" should be verified by temporarily introducing the bug and recording exactly what fails — this both proves the guarantee and reveals which layers have NO guard. Do the breaking in a SCRATCH COPY, never in the live tree. The obvious method — revert the real file in place, run the check, restore it — leaves a window that is short but real and entirely unattended: a crash, a rate limit, a killed session, a context limit, an interrupt, or a machine sleeping inside that window strands a tree where the fix is silently absent, the suite is green (because the reverted code is the old code passing the old tests), and the work looks finished. The failure is invisible precisely because nothing looks broken, and the cost is paid later by someone with no reason to look. Copy the tree (or file) to a scratch location, neutralise the guarantee THERE, confirm the break, and discard the copy — the real file is never in a state that an interruption can strand. The same rule covers every "temporarily break it to prove something" gesture: disabling a guard to demonstrate an exploit, commenting out validation to show what it catches, downgrading a dependency to reproduce a bug.

**Prefer a seam-injected proof that survives as an artifact.** A test that injects the old (unguarded) behaviour through a seam — a flag, a stub, an injected dependency — proves the same thing as a live revert and keeps proving it on every subsequent run, instead of being a claim in a commit message nobody can re-check after the fact. Treat "I will restore this in a moment" as the same risk class as an unreleased lock or an unclosed handle: a mutation with a deferred, mandatory undo, where the discipline is to arrange things so no undo is ever required.

**Apply when**: Any exhaustiveness/registry refactor, or any change whose claimed value is "this class of bug is now impossible," needs its guarantee proven by breaking it — in a scratch copy, never the live tree — and ideally pinned as a seam-injected regression test rather than a one-time manual check.

## Delegation Does Not Cover a Session's Own Orchestration Turns (2026-08-23)

**Learning**: When a top-tier model delegates implementation to cheaper-tier subagents, its own turns — reading to understand the problem, writing delegation briefs, reviewing what comes back, and go/no-go gates — are still billed at the top tier, and no amount of further delegation removes them: a session cannot spawn its way out of the turn it is currently taking. This overhead is invisible in a per-subagent cost view, which shows only the cheap delegated work, so it is worth measuring directly before concluding a delegation setup is efficient. Two corrections to the obvious inference: (1) orchestration is usually the THIN slice — reading, briefing, and reviewing are small next to implementation — so if delegation is genuinely working this overhead does not dominate, and treating the session's default model tier as the only lever overstates it; (2) a cheap default carries a cost in the other direction, because hard sessions then need manual escalation, which gets forgotten, and a mid-tier session orchestrating badly produces rework that exceeds the tier saving. Evidence from the session that produced this entry: the single largest waste was not tier at all — it was a duplicate subagent spawned to amend a task already in flight, which redid work still in progress and produced a stale report that had to be discarded (~80k tokens). A cost review that reaches for the model-tier explanation first will miss errors of that shape entirely.

**Apply when**: Assessing whether a delegation/subagent setup is actually saving tokens; reviewing a session for "this was expensive"; choosing a default model tier for new sessions; designing any hook or rule meant to control model-tier cost.

## Split the Rules File by CHURN, Not by Length (2026-08-26)

**Learning**: A project's rules file (CLAUDE.md, AGENTS.md, or equivalent) is loaded into every session, so it silently accumulates operational state until it is mostly runbook. The cut that matters is not "move the long sections" — it is: **what constrains how you WRITE code stays** in the rules file (voice, architecture, platform build constraints, do-not-regress gotchas), because an agent needs it *before* it starts and will otherwise reproduce the exact bug the rule exists to prevent; **what describes what is CURRENTLY TRUE moves out** to a sibling operational file (live state, the resolved-incident log, the work queue), because an agent goes *looking* for that once it has started. A soft pointer between the two is only safe for the second category — a pointer to knowledge an agent needs pre-emptively is worse than a long rules file, because the knowledge becomes both absent from context and out of sight; phrase such a pointer as a directive with a trigger ("read this before touching X, diagnosing a failure, or picking up work"), never as a passive "see also". Corollary: when the user states how their docs should be organised, that is a decision, not a suggestion to re-raise — flagging an oversized rules file a second time, after already being told what to do about it, is the same defect as deferring a fix to a closing summary.

**Apply when**: A rules file has grown large enough that most of its bulk is live/current-state content rather than write-time constraints; or a user has already given a structural instruction about doc organisation and a later session is tempted to re-flag the same issue instead of applying it. Cross-reference: "Memory-Write Discipline Is Required For Any AGENTS.md Divorce" is adjacent, not the same — that entry is about write BYPASS (memory-append paths leaking state back into the rules file); this one is about what content belongs in the file in the first place.

## A Safeguard That Cannot Evaluate Its Condition Must Refuse, Not Pass (2026-08-30 → 2026-08-31)

**Learning**: A control that cannot assess its own condition and returns the permissive answer anyway is worse than no control, because its presence stops the search — a reviewer sees a check, a suite sees green, and nobody looks further. Recurring shapes: a `catch` around a read that returns an empty collection, null, or false, collapsing "could not ask" into "asked, and the answer is nothing"; a parser whose per-line guards silently drop every malformed line and return an empty result without ever throwing; a response consumed without reading its status, so an error body is handled as a success payload; distinct failure modes (e.g. two different auth errors) collapsed into the same value a genuinely-empty success returns; a permission check aimed at the wrong object (a file, when the containing directory is what an attacker actually needs). Frame the fix at the point of CONSUMPTION: the distinct facts — "confirmed no", "confirmed empty", "could not tell" — must stay distinct at the moment code decides what to do next, and collapsing any of them into "proceed as normal" is worse than collapsing into "treat as failure", because emptiness is a legitimate answer the caller is entitled to trust. A named worked instance of the same law: a missing ML/OCR confidence score is UNKNOWN confidence, not high confidence — defaulting a missing score to a high value (e.g. 0.9) means every unscored item silently passes as confident; always default to 0 (reject) for safety/trust/verification scoring, because "reject on missing" is the only default a safeguard can give an input it never actually evaluated.

**The bound, which matters as much as the law**: applied without a stopping condition this justifies unbounded hardening — every unguarded path is a silent failure waiting, and there is always another one. Establish that the threat applies to a deployment that actually exists before building defenses for it; a real weakness in a configuration nobody runs is not a bug, and hardening a single-user local tool against a multi-tenant attack it will never face is indistinguishable from rigour while it happens — and costs the primary user a working default in exchange for an opt-out flag that disables a protection they never had.

**Apply when**: Reviewing any `catch` block, parser, or adapter for what it returns on failure versus emptiness; setting or reviewing a default for any confidence/trust/verification score; auditing a permission check for which filesystem object actually matters; and before hardening any code path, confirming the threat model it defends against matches a deployment that is real.

## A Failing Fix Is Evidence About the Diagnosis, Not Just the Fix (2026-08-30 → 2026-08-31)

**Learning**: When a prescribed fix fails, the reflex is to adjust the patch — the failure is usually saying something louder: that the diagnosis was wrong, one layer short, or right about a mechanism that was not the only one. The asymmetry worth internalising: a green re-run after a fix is WEAK evidence (the fix worked, or nothing exercised the case, or the assertion passes for a different reason than intended); a RED one is a free second opinion, because something concrete disagrees with a claim someone just made, before anyone has had time to believe the fix. Mutation-checking a fix — deliberately neutralising it and confirming the test goes red — turns a green run from an assumption into a measurement, but the sabotage must land where the assertion actually looks: same store, same process, same config, and upstream of any collapsing layer. A specific instance of that last trap is named in "A Collapsing Formatter Can Eat Your Regression Test's Control": a dedup/rollup layer can absorb exactly the defect a downstream assertion was meant to catch, so a disabled-guard control passes even though the guard is genuinely gone. The general form both share: before concluding anything from a mutation check, prove the mutation reached the code path the assertion actually reads — a control passing with the guard disabled is not evidence the guard is unnecessary, it is evidence the test cannot see the guard at all, which is worse than no test because it launders an untested pin into a proven-useless one.

**Apply when**: A fix does not resolve the reported failure — reopen the diagnosis before touching the patch; verifying any regression test's ability to fail — mutation-check it and confirm the sabotage lands upstream of any formatting/collapsing/aggregation layer between the code and the assertion; prescribing a fix to someone else — ask what BROKE, not just that the suite is green.

## An Optional Interface Method's Absence Is a Decision — Default It Toward the Safe Direction (2026-08-31 → 2026-09-01)

**Learning**: A composing wrapper sitting in front of several implementations of one interface forwards only the methods it knows to check for. When an interface method is OPTIONAL, "this instance doesn't implement it" and "the wrapper forgot to forward it" are indistinguishable from the caller's side — both read as absent. `instanceof` cannot rescue a caller trying to detect the capability, because no wrapper can ever satisfy an `instanceof` check against the class it wraps. The danger recurs once per optional method behind such a layer, and each instance is locally correct on the day it is written: one method's absence happens to route to the conservative fallback and nothing breaks; one method GATES a destructive inference (treat missing-and-unconfirmable as "assume gone, clean it up") and its silent absence through a new wrapper re-arms that destructive path with no type error anywhere; one method carries an operator-facing diagnosis and its absence degrades a specific, actionable error into a vague generic one.

**Remedies**: state the meaning of absence at the INTERFACE, not just at one call site — "not implemented", "not currently available", and "unknown" are different facts, and leaving every future caller to invent its own answer is how the ambiguity spreads. Default an optional method's absence toward the CONSERVATIVE behavior for whatever it gates — if the method's presence is what makes a destructive or irreversible action safe, its absence must block that action, never silently permit it. Detect a capability by duck-typing the method itself rather than `instanceof`, and audit every composing/wrapping layer against the interface's FULL optional-method list, not the subset its author happened to need.

**A different mechanism producing a related failure**: "Cross-Cutting Concerns Drop Quietly in Transport-Layer Refactors" describes the same silent-drop outcome arising from splitting one monolithic function into multiple transport-specific lanes rather than from a composing wrapper over an interface — audit logging, moderation, and security checks vanish on one lane because the new lane re-implements only the "main" logic. Different cause (fan-out by transport vs. optional-method forwarding), same shape of harm, same fix: an explicit checklist walked against every lane or every optional method, not memory.

**Apply when**: Defining any optional interface method — write down what its absence means, at the interface. Building any composing/wrapping layer over multiple implementations of one interface — audit it against the full optional-method list. Splitting a monolithic function into transport-specific lanes — checklist every cross-cutting concern the original had, on every new lane.

## State That Must Survive N Events Cannot Be Re-Derived From the Current Snapshot (2026-09-01)

**Learning**: A marking meant to persist until a specific future event — held pending confirmation, quarantined, in a grace period — computed by diffing newly-loaded input against the current live state is correct exactly once. On the SECOND application the marked thing is in neither set (it already left the live state on the first pass, and it was never coming back in the new input), the diff produces nothing, and the marking silently evaporates — the destructive default it existed to suppress resumes as though nothing had ever been held. This can be triggered by a completely idempotent operation: reloading the same unchanged input twice is enough to destroy the state, which is the worst possible shape, because the triggering gesture looks like a no-op. The tell is a rule expressed as a DIFF between two snapshots guarding an action that is IRREVERSIBLE — a diff answers "what changed just now," never "what is still owed from earlier," and the two get conflated because on the first iteration they give the same answer.

**Apply when**: A marking's meaning contains the word "until" ("hold until a restart", "suppress until confirmed", "keep for one more cycle") — that is lifetime state, not a snapshot difference; carry it forward explicitly across each event, or persist it on a durable row, and delete it only at the named event it waits for. The cheap general control: apply the same input twice and assert the state survives — a single-event test is exactly the test that passes on the broken version. Where the state cannot yet be persisted, add a second, independent backstop at the point the destructive action is taken, and name any call sites deliberately exempt from it.

## Push Your Own Commits From a Scratch Clone (2026-09-04)

**Learning**: In a working directory shared by concurrent sessions, a push carries every local commit including other people's. Never pull, rebase or stash the shared tree — `git stash` sweeps peers' in-flight edits, and a rebase refusing on their unstaged changes is a correct refusal to force past, not an obstacle to route around. Instead clone the shared repo to a scratch directory, add the real remote as `upstream`, check out a fresh branch from `upstream/main`, cherry-pick only your own commit sha(s) onto it, and push from that scratch clone. Two checks prove the result needs no re-testing: a matching `git patch-id --stable` between the original and cherry-picked commit proves the change itself is identical, and a matching `git rev-parse HEAD^{tree}` proves the resulting tree is byte-identical to what you'd have pushed from the shared tree — so a test run already performed against that tree still applies and does not need repeating.

**Apply when**: Committing or pushing from a working directory that other sessions or people are actively editing. Cross-reference: "Reverting a File That Swept In Someone Else's Work Destroys Their Working Copy Too" is the sibling hazard on the same shared-tree terrain (destroying a peer's uncommitted work via a bad revert, rather than via a bad push); "Multi-Session Shared-Tree Builds Need Deploy Windows, Not Just Lane Claims" is the complementary discipline for when several sessions must deploy from the same bundle rather than just avoid stepping on each other's commits.
