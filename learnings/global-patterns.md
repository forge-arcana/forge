## h-full vs min-h-full in Scroll-Container Chains (2026-06-02)
**Learning**: In a flex-column scroll container chain, `min-height: 100%` does NOT establish a height reference for children's `justify-center` — only `height: 100%` does. For cards that must both center short content AND allow expansion for dense content: chain is `overflow-y-auto (fixed height)` → `h-full` wrapper → `min-h-full` content div. The `min-h-full` expands for dense content (overflow handled by scroll container), while `justify-center` still works for short content because the div fills to its min-height.
**Apply when**: any scrollable card with vertically centered content that can also overflow.

## Scroll Content Inside Decorated/Framed Backgrounds — Structural Inset, Not Percentage Padding (2026-06-02)
**Learning**: When a scroll area's background image has decorative zones (borders, corner ornaments, framing), CSS padding-based safe zones fail — scrolled content flows freely through those zones regardless of padding. The reliable solution is a **structural inset**: outer div (`overflow-hidden` + background image), inner div (`position: absolute; top: X%; bottom: Y%; overflow-y-auto`), so content is physically bounded within the safe zone. CSS padding, `mask-image`, and gradient overlays are incomplete substitutes. Part of *why* padding fails for vertical clearance: **CSS percentage padding is width-based, not height-based** — `padding-top: 8%` (Tailwind `pt-[8%]`) computes to 8% of the containing block's *width*, not its height. On a tall portrait card (e.g. 360×640), `pt-[8%]` = 29px, far less than 8% of the 640px height (51px). If you must use percentage padding for vertical clearance, verify the absolute pixel equivalent and prefer `vh`-based or fixed-pixel values for height-sensitive clearances.
**Apply when**: any scrollable UI panel with a decorated/framed background image where content must not enter the decoration zone; and any vertical safe-zone or clearance calculation using percentage padding on portrait/mobile layouts.

## Show-Once Flag Must Be Written Inside the Async Callback (2026-06-02)
**Learning**: Writing a "seen" flag to localStorage BEFORE a setTimeout (or any async callback) fires permanently marks the event as triggered before it happens. If the user navigates away during the delay, the milestone/modal/notification is permanently suppressed. Pattern: write the flag INSIDE the callback with a re-check guard: `setTimeout(() => { if (!localStorage.getItem(key)) { localStorage.setItem(key, "1"); show(); } })`. The re-check also prevents double-firing when the same component is mounted twice (e.g. layout + page both render the same component).
**Apply when**: any "show once" modal, tooltip, or notification triggered by a timer, scroll event, or async callback using localStorage as the deduplication mechanism.

## WSL Path Compatibility (2026-03-15)
**Learning**: When running across Windows + WSL2, tool configuration that references directories must include all 3 path formats: Windows (`D:\`), WSL-mount (`/mnt/d/`), native Linux (`/root/dev/`). Without all three, permission prompts re-appear depending on which environment the session runs from.
**Apply when**: Setting up any tool that uses directory allow-lists on a WSL2 machine.


## Disable Rate Limiting in E2E Test Mode (2026-03-15)
**Learning**: E2E test suites run dozens of tests from a single IP in minutes, easily exceeding production rate limits. Gate rate limiting middleware with an environment check (e.g., `NODE_ENV !== "test"`) so tests aren't blocked. Rate limiting itself should have its own unit tests, not be tested implicitly via E2E.
**Apply when**: Adding rate limiting to a web server that has E2E tests.

## E2E Port Isolation from Dev Server (2026-03-15)
**Learning**: E2E test configs should use a dedicated test port constant or env var (e.g., `E2E_PORT`), never fall through to the dev server's `PORT`. With `reuseExistingServer: true`, tests silently connect to the running dev server instead of starting a fresh test server — causing mysterious failures from unrelated state.
**Apply when**: Configuring Playwright or similar E2E test runners in a project that also runs a dev server.

## Schema Enum Migration: Update All Raw SQL (2026-03-15)
**Learning**: After migrating string/text columns to database enums (pgEnum, MySQL ENUM, etc.), all raw SQL in test fixtures, E2E setup/cleanup, and seed scripts must be updated to use valid enum values. A value that worked with unconstrained text columns will throw constraint errors after migration.
**Apply when**: Converting text/varchar columns to enum types in any database.

## Test Factories Must Mirror DI Container (2026-03-15)
**Learning**: When adding a new service to the production DI container, always update test helper factories (e.g., `createTestApp`) to create and inject the same service. CI tests use the test factory, not the production startup — so a missing service causes `undefined` errors that only surface in CI, not local dev.
**Apply when**: Adding new services to a DI container in a project with separate test factory setup.

## Shared Package @/ Alias Breaks in Consumers (2026-03-19)
**Learning**: When app A's tsc processes files from a shared package via path mapping, the `@/` alias resolves using app A's tsconfig (not the shared package's). Fix: use relative imports in shared packages, never `@/` aliases.
**Apply when**: Creating shared packages in pnpm/npm workspaces with TypeScript path aliases.

## Cross-SPA Navigation Must Use window.location.href (2026-03-19)
**Learning**: In multi-SPA architectures (separate Vite builds per role), cross-role redirects (login, role-switch, route guards) must use `window.location.href`. Framework router `navigate()` only works within a single SPA boundary — it can't cross to a different Vite build.
**Apply when**: Building multi-SPA apps where different roles/portals are separate Vite builds.

## XHR withCredentials for Cookie-Based Auth (2026-03-19)
**Learning**: When using HttpOnly cookie sessions (Better Auth, etc.), XHR requests (file uploads) must set `xhr.withCredentials = true`. Without it, cookies aren't sent and the upload gets 401. `fetch` with `credentials: "include"` has the same requirement.
**Apply when**: Any file upload or XHR request in a cookie-based auth system.

## pnpm --filter: exec vs Script Name (2026-03-15)
**Learning**: `pnpm --filter <pkg> <arg>` treats `<arg>` as a package.json script name. To run a binary (tsx, tsc, vitest, etc.) scoped to a workspace package, use `pnpm --filter <pkg> exec <binary> <args>`. Without `exec`, pnpm fails with `ERR_PNPM_RECURSIVE_RUN_NO_SCRIPT`. This commonly bites CI workflows where commands are written as raw shell rather than package scripts.
**Apply when**: Running CLI tools scoped to a specific workspace package in a pnpm monorepo.

## Mobile Testing Progression: Browser → Emulator → Device → Store (2026-03-21)
**Learning**: Start mobile development testing in the browser (DevTools device mode, F12 → target device). As the product matures, build APKs for local device testing. For iteration velocity, lean heavily on emulators. Only pursue Play Store / App Store integration when the product is solid — store submissions have cost (developer accounts, review cycles, compliance), so readiness matters before that step.
**Apply when**: Setting up the testing strategy for any mobile-first or hybrid app project. Decide this progression on day one.

## Camera getUserMedia Succeeds But Produces Black Feed on Emulators (2026-03-21)
**Learning**: Android emulators with `hw.camera.back=emulated` return a valid MediaStream from `getUserMedia()` but produce a black/checkerboard feed — no error thrown, so `catch`-based fallbacks miss it. Fix: (1) use `hw.camera.back=virtualscene` for testable video, (2) always show manual-entry alongside the camera viewfinder (silent failure can't be reliably detected).
**Apply when**: Building camera features (QR scanner, barcode, photo) in hybrid apps tested on Android emulators.

## Android AVD Segregation Across Projects (2026-03-21)
**Learning**: Prefix AVDs with project name (`<project>-<role>`) to avoid collisions across projects sharing an Android SDK. Nuke commands must clean orphaned `.avd` data dirs under `ANDROID_AVD_HOME` — left behind when emulators run during `avdmanager delete`. Each project owns its own emulator config; no shared state.
**Apply when**: Setting up Android emulator workflows for Capacitor/hybrid projects in multi-project environments.

## TTS Economics: Cache, Stream, Treat as Primary Cost Driver (2026-03-29)
**Learning**: For voice-first apps, TTS API spend is typically the single biggest scaling cost — model it separately and identify the tier boundary where it dominates (often ~50% of total infra). Two practices keep it under control: (1) **persist audio on first generate** — store the rendered audio (base64 in a column or jsonb map keyed by content) and serve from storage on every replay; never regenerate the same text twice; (2) **stream when latency matters** — full TTS adds 3–5s for long messages. WebSocket streaming sends PCM chunks as they're generated; first audio plays in ~200–500ms via client-side AudioContext scheduling. Persistence kills cost; streaming kills wait. Voice playback opt-in is also a UX win (avoids uncanny valley).
**Apply when**: Any project with TTS — make these three decisions on day one (cost model, persistence layer, streaming vs blocking).

## Three-Layer Cost Architecture + Fire-and-Forget Processing (2026-03-21 / 2026-03-29)
**Learning**: For AI-powered apps with high-frequency input, separate processing into layers with different cost profiles: **free capture → cheap classification → expensive generation only on-demand**. Most user interactions touch only the cheap layers; the expensive layer fires only when the user explicitly asks. This is an architecture decision that IS a business decision — it makes the product viable for solo founders. The runtime expression is **fire-and-forget**: the capture response must feel instant (<200ms), so heavy processing (LLM classification, theme assignment, TTS pre-generation) fires *after* the response is sent, never blocking it. Use `promise.catch(() => {})` — don't await; the user sees results on next view. Capture is free/instant, processing is async/cheap, generation is on-demand/expensive.
**Apply when**: Designing any AI-powered product with high input frequency and heavy processing — layer processing by cost, make expensive layers on-demand, and fire heavy work in the background after an instant capture response.

## Offline-First Is Non-Negotiable for Capture Apps (2026-03-21)
**Learning**: When the core use case happens in a place with no internet (commute, underground, spotty signal), offline-first isn't a nice-to-have — it's the difference between the product working and not working. Auto-sync (not manual push) is correct because the whole point of a capture app is reducing cognitive load. Requiring the user to remember to sync defeats the purpose.
**Apply when**: If your primary use case happens offline, offline-first is table stakes.

## Trust Ladder Onboarding for Sensitive Features (2026-03-21)
**Learning**: When a product requires sensitive data (voice biometrics, diary-level thoughts), don't ask for everything upfront. Build a trust ladder: deliver core value first (basic features), then progressively unlock sensitive features (voice input → voice customization). The user should feel "of course I'll give you this" by the time you ask, not "why do you need this?"
**Apply when**: Any app requiring biometric or deeply personal data — design the onboarding progression.

## Modes as a Volume Dial, Not Separate Machines (2026-03-21)
**Learning**: When a product has multiple "modes" of interaction, check whether these are genuinely different processing pipelines or just different amounts of the same processing. Often all modes use the same engine — the mode is injected as context into one system prompt. This avoids maintaining N separate AI pipelines. The modes are a "volume dial" of AI involvement: from zero (quick action) to full (open dialogue with history).
**Apply when**: Prefer one adaptive system over many specialized systems when the variation is in degree, not kind.

## Provider Factory Consistency (2026-03-21)
**Learning**: When a codebase establishes a provider factory pattern (e.g., `createProvider<T>(envKey, registry, fallback)`), ALL environment-driven service selection should use it — including rate limit stores, cache backends, and queue implementations. Inconsistent ad-hoc if/else selection for one provider while others use the factory creates maintenance confusion and makes the pattern untrustworthy.
**Apply when**: Adding new environment-switchable services to a codebase that already has a factory pattern.

## ML/OCR Confidence Defaults Must Reject, Not Pass (2026-03-21)
**Learning**: Defaulting missing confidence scores to a HIGH value (e.g., 0.9) means unscored items silently pass as confident. Always default to 0 (reject by default) for safety/trust/verification scoring. A missing score is unknown confidence — treating it as high confidence is a silent bug.
**Apply when**: Reviewing default values for ML confidence scores, trust scores, verification scores, or any probability-based threshold.

## AI Timestamps Are Unreliable (2026-03-26)
**Learning**: Do not add conventions requiring AI agents to prefix messages with wall-clock timestamps (e.g., `[HH:MM]`) or report elapsed times after tool calls. The agent's reported times are not accurate and add noise without value. If timing matters, instrument it at the tool/platform level, not in agent output formatting.
**Apply when**: Designing output formatting conventions for AI agents or reviewing proposals that include timestamp requirements.


## Real-Time WebSocket ≠ Push Notifications (2026-03-26)
**Learning**: WebSocket real-time (Ably, Pusher, Socket.io) and push notifications (FCM/APNs) solve different problems. WebSockets deliver updates while the app is open — they require an active connection. Push notifications reach users when the app is closed or backgrounded — they require platform-specific infrastructure (Firebase project, APNs key, server-side device token storage). For pilot/MVP launches with small user bases, WebSocket real-time is sufficient. Push notifications add significant infrastructure complexity (two vendor integrations, token lifecycle management, platform review requirements) and can be deferred to a post-launch sprint informed by real engagement data.
**Apply when**: Scoping real-time features for mobile apps. Don't conflate "real-time updates" with "push notifications" — decide which you actually need for launch.

## Configurable Paths via Resolution Chain (2026-03-15)
**Learning**: Never hardcode absolute paths in portable tools or skills. Use a resolution chain: (1) env var, (2) config file entry, (3) fallback default. This makes tools portable across machines and environments.
**Apply when**: Any tool or skill references a directory that varies by machine (repos, config dirs, data dirs).

## Global Config Over Per-Project Duplication (2026-03-15)
**Learning**: When a tool supports both global and per-project configuration, put all standard settings in the global config. Only create per-project config for overrides. Duplicating the full config into every project is a DRY violation that creates drift and maintenance burden.
**Apply when**: Setting up project-level configuration files for tools that also have a global config.

## Android 15 Edge-to-Edge Status Bar Overlap in Capacitor (2026-03-22)
**Learning**: Android 15 (API 35) enforces edge-to-edge rendering by default — app content renders behind the status bar. `StatusBar.setOverlaysWebView({ overlay: false })` is silently ignored. CSS `env(safe-area-inset-top)` returns `0px` on Android WebView (only `safe-area-inset-bottom` works). `WindowCompat.setDecorFitsSystemWindows(window, true)` in MainActivity also fails — Capacitor's BridgeActivity overrides it. The only working fix in Capacitor 7 is `android: { adjustMarginsForEdgeToEdge: "force" }` in `capacitor.config.ts`. Do NOT stack multiple fixes — they each add padding independently, causing a visible gap. (**Capacitor 8 removed this config** — it ships a System Bars core plugin that manages insets via CSS `env(safe-area-inset-*)`, and Android 16/API 36 makes edge-to-edge mandatory; see the stack guide's Capacitor section.)
**Apply when**: Building Capacitor 7 Android apps targeting API 35+ where content overlaps system status bar (on Cap 8, use System Bars instead).

## Bidirectional Sync System Design (2026-03-28)
**Learning**: When designing any system that syncs files between a source-of-truth repo and deployed copies (skills, configs, knowledge), six rules must hold together:
1. **Three-way comparison** — source vs manifest vs deployed, so you can distinguish "source updated" (deploy it), "deployed updated" (reverse-sync it back), "both updated" (conflict, manual review), "neither" (skip). A two-way comparison can't tell which side moved without a baseline.
2. **Atomic edit-then-deploy** — direct source edits must immediately re-deploy to targets; otherwise a concurrent absorption run sees DIFFERS, treats the stale deployed copy as "newer," and silently reverts the source edit.
3. **Reverse-sync writes to source, never to deployed** — writing to deployed copies creates a permanent gap (deployed has more entries than source) that re-running cannot heal because trackers mark entries as already processed.
4. **Idempotent absorption tracker** — when absorbing entries from a source you don't own (append-only logs, learning files, changelogs), maintain a tracker (content hashes or titles) of already-processed entries so each run only evaluates new material.
5. **Self-flagging entries beat heuristic triage** — when a producing skill writes learnings, it should self-classify each as "promote-worthy" or "local-only" at write time; downstream consumers auto-promote without guessing.
6. **Don't duplicate the layer above** — forward-sync deploying conventions into a project workspace must check whether the global config layer already covers the convention before adding a project-level copy. Duplicating rules across layers creates drift.
**Apply when**: Designing or operating any bidirectional sync system (deploy + absorb) between a canonical repo and its consumers.

## Skills Own Their Dependencies and Their Discovery (2026-03-26)
**Learning**: A skill package must be self-contained in two senses. (1) **Dependencies**: any framework or reference doc the skill cites must live inside the skill's directory, not at repo root. Static reference docs in shared locations become stale orphans because the skill self-iterates but the orphan doesn't — co-location ensures everything evolves together. (2) **Discovery**: when a skill needs to be discoverable on fresh clone before global deployment, use a thin bootstrap file in the project's local skill directory (~3 lines) that points to the real skill file. Avoids symlinks (OS-dependent) and full duplication (drift risk).
**Apply when**: Structuring skill or plugin directories in any repo that is itself the source of truth for those skills.

## Firebase API Key Restriction for Public Repos (2026-03-29)
**Learning**: Firebase API keys are project identifiers (not secrets), but in public repos, ALWAYS restrict the key to the deployment domain via Google Cloud API Keys API. Add HTTP referrer restrictions (deployment domain + `localhost/*` + `127.0.0.1/*`). Security rules protect data integrity, but unrestricted keys let unauthorized apps consume quota or abuse Firebase resources from other origins.
**Apply when**: Setting up Firebase in any project, especially public repos or GitHub Pages sites.

## Silent Browser API Failures — Check Security Headers FIRST (2026-03-29)
**Learning**: When a browser API (`getUserMedia`, `Notification.requestPermission`, `navigator.geolocation`) fails silently — no prompt, no error UI, just a quiet `NotAllowedError` — the root cause is almost always a `Permissions-Policy` response header blocking it. `curl -sI <url> | grep -i permissions-policy` is step 0 before reading any client code. The HTML `capture` attribute on `<input type="file">` is also silently ignored when the policy blocks camera.
**Apply when**: Any browser API behaves as if the user denied permission but no prompt was ever shown.

## Bot and Crawler Protection Strategy (2026-03-29)
**Learning**: Block crawlers at every non-production tier and on every authenticated production surface — not just staging. Internal-only environments should layer all defenses (`robots.txt Disallow`, `X-Robots-Tag: noindex,nofollow` header, infrastructure-level auth gating, `noindex` meta). Customer-facing pre-prod that needs unauthenticated user access can only use app-level headers — infrastructure auth gating locks out the real users you're trying to test with. Production: allow crawling only on truly public pages (marketing, docs); every authenticated path gets `X-Robots-Tag: noindex` plus `Disallow` rules. A bot reaching an admin panel is a security incident, not an SEO miss. Platform-specific gating commands belong in a stack guide, not in this evergreen learning.
**Apply when**: Deploying any application. Decide upfront whether each environment needs unauthenticated end-user access — that decision dictates whether infrastructure gating or app-level headers is correct.

## Next.js 16 Process Renaming Breaks Zombie Kill Scripts (2026-03-29)
**Learning**: Next.js 16 renames its dev server process to `next-server (v16.x.x)` — a custom process title with no `node`, `next dev`, or project name in the command string. Standard pgrep patterns (`node.*next.*dev`, `node.*(next|playwright).*<project>`) miss it entirely. The process also auto-selects non-standard ports when the configured port is busy, so port-based `fuser -k` also misses it. Kill/restart scripts must match the literal string `next-server` and scope to the project by checking `/proc/$PID/cwd`.
**Apply when**: Writing or updating restart/kill-zombie scripts for any Next.js 16+ project. The `/srs` skill templates need this pattern.

## Voice Clone Consent Flow Is a Legal Requirement (2026-03-29)
**Learning**: Voice biometrics are sensitive data under GDPR, UK DPA, and emerging US state laws. Before cloning a user's voice, present a dedicated consent screen with: what you collect (audio sample), how it's used (private TTS only), user rights (delete anytime), and third-party processing disclosure (name the provider). Use a checkbox-based explicit consent mechanism — implied consent from "tapping record" is insufficient.
**Apply when**: Any feature that processes voice biometrics — clone, voiceprint, speaker ID. Not needed for plain speech-to-text.

## Auth Library Territory: Don't Recreate, Don't Bypass (2026-03-29)
**Learning**: Any auth library that manages its own user/session/account tables owns identity, sessions, password hashing, and credential validation. Two anti-patterns to avoid together: (1) **never create a parallel "user-like" table** with overlapping fields (email, name, provider ID) — FK directly to the auth library's user table, extend via the library's own field-extension mechanism if supported, or use a thin profile table with only app-specific fields. (2) **never hand-craft sessions for mock/staging login** — use the library's own sign-in method and seed credentials via the library's own password-hash function. Unsigned cookies you craft by hand won't verify when the auth middleware checks them. If you're writing `response.cookies.set("session_token", ...)` in a mock auth route, STOP. The library is the single source of truth for identity AND for session shape.
**Apply when**: Designing schemas or building staging/dev mock login for any project using an auth library with its own user table.

## Cloud Services Must Have Local Dev Fallbacks (2026-03-29)
**Learning**: Every cloud service call (GCS, S3, email, push notifications) needs an env-gated local fallback. Write the local branch FIRST. Three tiers: local dev = filesystem/mock/console.log, staging = real cloud service, prod = real cloud service. Module-scope cloud client instantiation without an env check (`new Storage()`) crashes local dev immediately.
**Apply when**: File uploads, email sending, push notifications, or any external service integration. The local fallback is step 1, not step last.

## Read-Only Auth Routes Must Be Excluded from Mutation Rate Limits (2026-03-29)
**Learning**: Rate limiting `/api/auth/*` by URL prefix catches read-only GET endpoints (session checks, user lists, config) alongside mutations (login, signup, verify). After a normal login+logout cycle exhausts the auth budget, GET endpoints return 429, breaking UI features. Better pattern: rate limit by HTTP method — only POST/PUT/DELETE on auth paths get the strict limit; GET gets the default limit.
**Apply when**: Adding rate limiting middleware that matches URL prefixes, or adding new routes under a rate-limited prefix. Always check if the new route is read-only.

## No Auto-CI for Solo Dev Projects (2026-04-03)
**Learning**: Solo dev projects should use `workflow_dispatch` (manual trigger) for CI, not auto-trigger on push/PR. Run CI explicitly via `/cicd` or `/ponci` when ready. Auto-CI wastes Actions minutes and creates noise during rapid iteration where every push is WIP.
**Apply when**: Setting up CI for any solo dev project. Default to manual trigger unless the user explicitly wants auto-CI on every push.
**Evolved by**: "The Local Pre-Commit Gate Must Be Command-Identical to the Deploy Build" (2026-07-18) — adds the missing condition: never retire or downgrade a remote CI whose checks you haven't first relocated into the local gate.

## GCP Artifact Registry Cleanup Policy Must Be Set Per-Repo (2026-04-16)
**Learning**: Artifact Registry cleanup policies are per-repository only — no project-level default. Every new Docker repo starts with NO cleanup policy. Old images accumulate silently and cost money. Standard policy: keep last 5 versions, delete rest (`{"action":{"type":"Keep"},"mostRecentVersions":{"keepCount":5}}` + `{"action":{"type":"Delete"},"condition":{"tagState":"ANY"}}`). Apply immediately on repo creation via `gcloud artifacts repositories set-cleanup-policies`.
**Apply when**: Any blueprint or deploy script that creates Artifact Registry repos for Cloud Run. Should be a checklist item in GCP deploy setup.

## Pipeline Silent-Failure Alerts: "Last Produced Output" Metric (2026-04-16)
**Learning**: A scraping/ingestion pipeline can run cleanly and log success for weeks while producing zero documents — if the listing-discovery layer is broken. "Last successful run" is necessary but insufficient. Add a per-source "days since last new document" alert. Silent discovery failure is a real failure mode that unit tests and HTTP status checks will never catch.
**Apply when**: Designing observability for any source→sink pipeline. Add a "last produced output" metric alongside "last successful run."

## Single-Use Refresh Tokens Race Under Concurrent Processes (2026-04-26)
**Learning**: When several processes share one OAuth credential and the provider issues *single-use* (rotating) refresh tokens, simultaneous expiry triggers a race: each process refreshes with the same refresh token, the first wins, the rest get `invalid_grant` and crash. The durable client-side fix is a **cross-process lock on the credential write** — refresh under a lock, re-read fresh inside it, and preserve the existing refresh token if the provider's response omits one (RFC 6749 §6). A proactive scheduled-refresher is a lighter mitigation, but if you build one, mind three traps: (1) **scheduled, not polling** — sleep until `expiresAt - margin`, refresh once, recompute; (2) **the refresher races itself** — serialize bursts via non-blocking `flock -n`, exit on lock loss; (3) **clock-skew on suspend** — re-read `expiresAt` on every wake. (Historical note: Claude Code hit exactly this race with concurrent subagent fan-out; it was fixed upstream in v2.1.136 via a cross-process credential lock. Forge's WA-001 mitigation was retired when that shipped.)
**Apply when**: Designing or reviewing any multi-process system that shares a rotating OAuth credential — your own SDK integrations, not Claude Code (which now handles it internally).

## Exhibit A — How a Project-Name Leak Happens (2026-04-25)
**Learning**: A `/forge` fold-phase run absorbed seven learnings from a project session and committed them with the project name, the contributor's full name, the local currency price, project schema field names, a competitor product name, and region-specific framing all preserved verbatim. Even the commit title named the project and the person. Three layers of "no project names" rules (forge `CLAUDE.md` HARD RULE, `skills/forge/SKILL.md` Phase 3 instructions, "No Project Names Rule" footer) were prose instructions the agent was supposed to follow on its honor — there was no scanner, no reject step, and `Forge-worthy: yes` was treated as a citation slot rather than a flag. Worse, prior `/cast` improvements had wired contributor attribution into PLAN/DONE *tables*, and the agent generalized that to mean attribution belongs in absorbed *content* too. The boundary was lost.

**Lessons baked into the fix**:
1. Prose rules without enforcement get ignored when the agent is mid-flow. A literal scanner (`scripts/fold-purity-check.sh`) now runs in fold phases 3e and 3i and on commit messages, blocking writes with non-zero exit if it detects: currency-symbol prices, attribution lines (`contributor:`, `(<X> session, YYYY-MM-DD)`), CamelCase compound names not on an allowlist, project schema names in backticks, or `Firstname Lastname` patterns in body text.
2. Attribution lives in the PLAN/DONE table, NEVER in the absorbed content body. `Forge-worthy: yes` is a flag, not a citation slot.
3. The first cure for a precedent leak is to canonize it as the cautionary example future runs read in pre-flight.

**Apply when**: Authoring or modifying any forge fold logic. Reviewing any commit that touches `<forge>/learnings/` or `<forge>/memory/`. When rules are repeatedly violated despite being documented in HARD RULE form, the next layer is mechanical enforcement, not louder prose.

## DNS, Email, and App Hosting Are Fully Decoupled — Don't Bundle Them (2026-04-22)
**Learning**: Domain registration, DNS hosting, email hosting, and application hosting are four independent decisions. Users (and sometimes agents) instinctively bundle them — "we're deploying to GCP, so we should get Google Workspace" or "the registrar offers email, so use theirs." This bundling is almost always wrong for bootstrapped projects. GCP/AWS/Vercel don't care where DNS lives; they only need records pointing at them. Email providers don't care where the domain is registered; they only need MX/SPF/DKIM/DMARC records in whatever DNS you use. Each layer should be chosen on its own merits (cost, features, lock-in). The only coupling is convenience: same-vendor domain verification is slightly faster, but never worth paying a markup for.
**Apply when**: Any "what should I use for X" question touching domains, DNS, email, or hosting. Before recommending a bundle, decompose into the four independent layers and price each separately. Challenge any "we need X because we're using Y" reasoning unless Y literally requires X.

## Cloudflare Registrar + Email Routing Is the Default Bootstrap Stack (2026-04-22)
**Learning**: For any bootstrapped project (solo founder, small team, pre-revenue), the default stack is: Cloudflare Registrar (at-cost domain pricing, no markup — typically the cheapest available for major TLDs) + Cloudflare DNS (free, fastest anycast) + Cloudflare Email Routing (free forwarding to a personal mailbox) + whatever app host fits the workload. Total cost is the registration fee plus zero. Managed productivity suites (per-user-per-month inbox + collaboration) are premature for a single founder — email forwarding plus a "Send As" identity in a personal mailbox (via a free SMTP relay) covers send + receive. Upgrade triggers are concrete: (1) hiring, (2) needing shared inboxes like `support@`, (3) needing org-grade Docs/Drive/Meet collaboration. ## Grep Defaults Are Tuned for Humans, Not Token-Metered Agents (2026-05-01)
**Learning**: The Grep tool's default `output_mode: "content"` mirrors Unix `grep` — sensible for a human skimming output, wasteful for an LLM that pays per token to read every returned line. The analogy "grep has worked this way for 50 years" doesn't hold: a Unix tool returns bytes to a free reader; an agent tool returns tokens to a metered one. Default behavior should be the cheapest shape that preserves correctness, with verbosity opted *into*, not out of.
**Apply when**: Any Grep call. Decision order:
  1. **Default to `output_mode: "files_with_matches"`** — paths only. 10-100x fewer tokens. Sufficient for "where is X defined / referenced."
  2. **Use `output_mode: "content"` only when surrounding lines matter for reasoning** (e.g., understanding how a symbol is used, not just where).
  3. **Always set `head_limit`** when you expect more than a handful of hits. Unbounded content searches are the worst offender.
  4. **For broad sweeps (>50 expected hits, or open-ended "find anything related to X")**, delegate to an exploration subagent — its context is isolated, only the summary crosses back.
  5. **For known symbols/paths**, prefer Read or `rg` via Bash with tight flags over Grep — direct lookups don't need the tool's full result formatting.

## AGENTS.md Is the Cross-Tool Standard; Per-Vendor Adapters Are a Soft Lock-In (2026-05-09)
**Learning**: When building tooling that targets multiple AI coding agents, the temptation is to build per-vendor adapters that emit each tool's specific config (a Claude-coupled rules file, a Cursor rules file, a Copilot instructions file, per-vendor command directories, etc.). This is a softer flavor of vendor lock-in: the tooling multiplies by the cardinality of the vendor matrix, drifts apart over time, and silently couples the build pipeline to whichever adapter manifests are maintained. The actual answer is **`AGENTS.md`** — an open standard stewarded by the Agentic AI Foundation under the Linux Foundation, adopted by tens of thousands of open-source projects. Plain markdown, no required schema, no YAML frontmatter. Most agent CLIs read it natively. For agents that don't yet read `AGENTS.md` natively, a thin bootstrap (a one-line `@AGENTS.md` import in the vendor's expected file, or a symlink) is enough — zero behavior change, no per-vendor build path. One source, one universal output, plus a tiny per-tool bootstrap only where the vendor genuinely cannot read AGENTS.md.
**Apply when**: Designing or evaluating tooling that produces config for multiple coding agents. **Default to AGENTS.md** as the single output. **Reject per-vendor adapters** unless a vendor genuinely cannot read AGENTS.md. Keep vendor-specific surfaces (permissions, MCP, hooks) as opt-in helpers, not in the main build. **Anti-pattern**: a build pipeline with one target per vendor (`build vendor-a`, `build vendor-b`, …) — that's the lock-in trap with extra steps.

## Memory-Write Discipline Is Required For Any AGENTS.md Divorce (2026-05-09)
**Learning**: Divorcing a vendor-specific rules file from `AGENTS.md` (whether via symlink or via a 1-line `@AGENTS.md` import) is fragile because most agent harnesses provide memory-append paths that bypass the abstraction — keyboard shortcuts, slash commands, and init/regen tools that write directly to the vendor file with no target override and no awareness of imports/symlinks. There is typically no settings option to redirect these writes. Without an explicit discipline rule in AGENTS.md, repeated memory-append invocations slowly pollute either the thin pointer file (with `@-import`) or the rules file itself (with symlink — since the write transparently lands in AGENTS.md). Either way, the cosmetic divorce erodes back into the same vendor-coupled blob over time. The fix is *not* technical — it's a codified rule + behavior change.
**Apply when**: Setting up an AGENTS.md divorce in any project. Always include a "Memory write discipline" section in AGENTS.md stating: (1) AGENTS.md is rules, not storage; (2) memory storage lives in `memory/` (always-on) or `<sphere>/memory/` (sphere-scoped); (3) users must NOT use the harness's direct memory-append paths — instead, ask the agent to "remember X" so it saves via auto-memory (which lands in `memory/`, divorce-safe). Bonus: bake a janitor scan into the pre-commit ritual that walks every vendor rules file in the repo and flags any content beyond the bare `@AGENTS.md` line / symlink target — catches the bypass before commit.

## Multi-Sphere Vaults: Per-Sphere AGENTS.md + Per-Sphere memory/ Makes Focus Convention Structural (2026-05-09)
**Learning**: Multi-domain vaults (one repo containing many semi-independent peer subdirs) benefit from giving each sphere its own `AGENTS.md` + its own `memory/MEMORY.md` index, with sphere-scoped memory files inside the sphere's `memory/` dir (sphere prefix dropped from filenames since the path encodes sphere). The root `memory/MEMORY.md` becomes a thin index: always-on entries (load every conversation) + a pointer table per sphere ("for sphere-X memory, see `<sphere-x>/memory/MEMORY.md`"). Sphere AGENTS.md files reference their local `memory/MEMORY.md`. The win: the **focus convention becomes structural rather than procedural** — agents reading `<sphere>/AGENTS.md` literally only see that sphere's memory; off-sphere entries are physically out of sight, not just behind a "don't read this" rule. Bonus: `git add <sphere>/` captures everything sphere-related (rules, memory, content) in one diff scope.
**Apply when**: Divorcing a multi-sphere vault (or any repo with peer-equal subdirs that are semi-independent domains). Single-domain projects don't need this — a flat root-level `AGENTS.md` + root `memory/` is fine. The pattern only earns its keep when the project has 3+ peer domains AND memory accumulates per-domain. For harnesses with auto-loading subdir rules files (e.g., a one-line `@AGENTS.md` pointer in each sphere's vendor file), the cross-tool divorce composes cleanly with the harness's existing auto-load behavior.

## Evaluating New Model Classes for a Serving Gateway — Probe Hardware First, Slot as a Tier (2026-06-13)
**Learning**: When evaluating a new model class (diffusion, MoE, distilled) for an existing serving stack, the load-bearing constraints are (1) **VRAM fit on the actual target hardware** and (2) **runtime support in the current serving path** — not headline quality. Probe the real GPU empirically before designing it in; do not trust a remembered spec. Two memory traps: a **text-diffusion** model wins on throughput (parallel block denoising), native infilling (fill-the-middle), and format/length controllability but trades away raw quality versus autoregressive peers of similar size — so slot it as a new fast/edit tier (best fit: code/markup generation with edit loops and structured output; worst fit: language-fidelity-sensitive paths where a domain-specialist autoregressive model already exists), never as the quality anchor. A **MoE** model's "active params" (e.g. 4B of 26B) mislead on memory: all experts must be resident, so footprint tracks *total* parameters, not the active subset — a small active count is not a small-VRAM model. When the local box can't fit even quantized weights, route the model to where the stack already has headroom (cloud) rather than bridge-hacking it onto undersized hardware.
**Apply when**: assessing a new model class (diffusion, MoE, distilled) for adoption into a tiered or multi-provider inference gateway, or deciding local-vs-cloud placement. Verify on the real serving substrate before designing it in. Pairs with detect-don't-ask: confirm hardware empirically before committing to an architecture.

## Background Orchestrations Die With the Host Session — Design for Resume-by-ID + Durable Incremental Writes (2026-06-28)
**Learning**: A long-running background orchestration (a multi-agent workflow, an async sub-agent, any detached job spawned inside an interactive agent harness) is bound to the host process/session. When that session disconnects or the process exits — a laptop sleeping, a mobile client backgrounding, a tab closing — in-flight work stops with no completion record, even though the harness reported it as "launched." Two properties decide whether this is a setback or a catastrophe: (1) whether each unit of work writes its output to durable storage *as it finishes* (so partial progress survives), and (2) whether the orchestration is *resumable by id* with already-completed steps returning cached results. Designs that buffer all output until a final flush lose everything on disconnect; designs where each step commits its artifact immediately lose only the in-flight step, and a resume re-runs from the first incomplete step. The cost of a disconnect then becomes time, never correctness.
**Apply when**: Launching long background workflows or async agents from a disconnect-prone session (mobile, web, anything not a stable terminal), or spawning any agent for data generation / bulk file creation expected to run more than a few minutes. Prefer orchestration that journals step results and resumes by run-id; have each step write durable artifacts incrementally rather than at the end; and on a "no completion record" notice, inspect what landed on disk before relaunching — then resume rather than restart. Durable incremental writes do not happen by default in a delegated agent — **instruct it explicitly in its prompt**: "Write incrementally — append every 20-50 items. Do NOT buffer everything and write at the end." The pattern is generate batch → append → generate next batch → append.

## Public Static API From Private Source — Split Private Builder + Public Mirror, One-Way Deploy-Key Sync (2026-06-28)
**Learning**: To expose a public, keyless, CDN-served static-data API while keeping the build logic, fallback strategy, and raw inputs private, one repo cannot do it — public static hosts that serve straight from a VCS only serve *public* repositories, so a private repo has no public path. The pattern is two repos: a **private source repo** (builder, source registry, raw landing zone, automation) and a **public mirror repo** holding only the consumer surface (the data, its schemas, a discovery catalog, the long-form archive). The build runs in private and syncs the allow-listed public paths into the mirror over a **write-scoped deploy key**. The path allow-list *is* the security boundary — it must be an explicit include-list in one script, never an exclude-list, so a new private artifact is private by default. Provenance (which upstream sources contributed) stays public because it is what makes the data trustworthy and is often required by source-attribution terms; only the *method* is hidden.
**Apply when**: You want a public dataset/API but must keep build internals, competitive logic, or raw third-party payloads private. Use a private builder + public mirror, sync one-way via a write-scoped deploy key for the high-frequency path and a separate narrowly-scoped token only where an API (e.g. release uploads) genuinely needs it, and make the public surface an explicit include-list in one script that doubles as the audited public/private boundary.

## Delimited Feeds With Free-Text Columns — Index Stable Fields From the End, Not the Front (2026-06-28)
**Learning**: When parsing a delimited feed (CSV/TSV/SDMX) where a free-text column (a title, description, or label) can contain the delimiter and the upstream does not reliably quote it, front-indexing the value/timestamp columns silently corrupts or drops rows the moment a delimiter appears in that free-text field (a label rendered "City, Country" injects an extra separator, shifting every subsequent front-indexed column by one). The robust technique is to address the stable trailing columns (the value, the period, status flags) by **offset from the END of the row**, and the stable leading keys (before the free-text field) by offset from the front. A delimiter injected into the middle field then shifts only the fields between the two anchors — never the value or date. Pair this with a length check that *tolerates extra* fields (count >= header length) rather than rejecting rows whose count differs, since the naive "field count must equal header" guard is exactly what drops the injected-delimiter rows.
**Apply when**: Parsing any externally-sourced delimited data where a descriptive column may contain the delimiter and quoting is unreliable. Anchor leading keys from the front and trailing values from the end, derive the trailing offsets from the header so the parse also survives column-order changes, and never use exact-field-count as a row-validity gate when free-text columns are present.

## Time-Series File Archives — Partition by Effective Date + Dedupe, Not Ingest Date (2026-06-28)
**Learning**: A file-based, append-only time-series archive (one shard per day in a VCS or object store, rebuilt on a schedule) duplicates data badly if it partitions by *ingest/build date* while each record carries its own *effective date*. Slow-moving or carried-forward values (a weekend rate, a policy figure unchanged for a year) get re-emitted into every build's partition, so a downstream "all values for entity X" query returns N copies per effective date and the cold-tier roll-up accumulates duplicates without bound. The fix is to partition by each record's **own effective date** and make each partition file idempotent: on write, merge with what is there, dedupe on the natural key (date, entity, field) with the freshest build winning, and emit sorted. Then a value re-observed across many runs is recorded exactly once, an unchanged day rewrites byte-identical content (so the VCS sees no diff), and re-runs are safe. The row *count* stays bounded by distinct observations, not by the number of builds — which is the property to assert in a test.
**Apply when**: Building any file/VCS-based time-series archive that rebuilds on a schedule and whose records have an effective date distinct from the ingest date. Partition by effective date, dedupe on the natural key per partition, and verify idempotency by asserting the total row count is stable across repeated rebuilds.

## LLM Cost Capture Is Four-Dimensional (2026-07-04)
**Learning**: Per-call cost actuals computed as input×rate + output×rate misprice every cached call: cache reads bill at roughly a tenth of the input rate, cache writes at a premium over it, and the input-token count excludes the cached prefix. Any spend ledger fed by LLM calls must price all four usage fields at their distinct rates, store the model ID plus a rate-effective-date per entry (intro pricing windows and quarterly model turnover corrupt historical entries otherwise), persist the provider request id for tracing, and verify caching actually engages (cache-read tokens > 0) since prefixes below the model's minimum cacheable length silently don't cache.
**Apply when**: Any product metering LLM spend per tenant, feature, or item — design the ledger schema around the full usage object before the first call is billed.

## Instagram Publishing Does Not Require a Facebook Page — Pick the Login Path by Footprint (2026-07-05)
**Learning**: When a brand has no Facebook presence, do NOT stand up a hidden/empty Facebook Page just to publish to Instagram. ## Development-Mode Platform Apps Only Serve Accounts Holding a Role (2026-07-05)
**Learning**: After a textbook-perfect OAuth (token issued, all scopes granted), **every** API call can still fail with one blanket error — e.g. `{"error":{"message":"Unsupported request - method type: get/post","code":100}}` on every endpoint including identity reads and token exchange. This is not a method, endpoint, version, host, or HTTP-client bug: it is the app's **authorization state**. While a platform app sits in **Development mode**, its API only serves accounts that hold a **role** on the app. The fix is a dashboard step, not a code change: add the account under App roles → testers, then **accept the invite from inside the platform's own app**; every call starts working instantly — no App Review, no Live mode. The generalizable tell: a *uniform* error across endpoints that a valid token should reach means "this account isn't authorized on this app yet," not "this call is malformed." Misleading diagnoses that cost hours and should be skipped: identity alias vs numeric id, API version, personal-vs-professional account type, sandbox mode — none of them produce or fix it. App Review is about reaching *other people's* accounts; self-publishing to an owned account needs only the role in Development mode.
**Apply when**: Any platform integration (social, payments, messaging) where a freshly-authorized token gets a uniform error on every endpoint. Check the app's mode and the account's role on it before debugging the request shape.

## Burst-Throttled Media APIs: Space the Calls, and Never Retry a Lockout That Resets (2026-07-09)
**Learning**: A media-publishing API can throttle **rapid-fire creation** in a way that hits multi-item posts far harder than single-item ones, because a multi-item post fires many calls in a ~1-2s burst (one container-create per child + a parent create + publish) while a single post fires one. The result reads like an account-wide block but is media-type-specific: quota is nowhere near its limit and the token is valid, yet one post type fails while others on the same account succeed. **Always split failures by media type before concluding the integration is blocked.** Also check the platform's own quota endpoint before blaming a daily cap — quota is usually nowhere near its limit. Three fixes compound: (1) sleep a few seconds between per-child container creates; (2) don't poll child containers that are ready instantly — per-child status GETs add burst that helps trip the throttle; poll only the parent and genuinely-async (video) containers; (3) **the trap** — such a lockout can last ~24h and **reset on every attempt made during it**, so a retry cron or a manual "let me just try again" restarts the clock and the block never clears. Honor the provider's transient flag: a non-transient error must be dropped after ONE attempt, never retried, and a windowed publisher needs a **media-type-specific cooldown** that holds the offending type while letting others flow. There is no force-clear and no regain-time header — only elapsed clean time works.
**Apply when**: Any scheduled publisher hitting a third-party media API, especially multi-item posts. Design per-type cooldowns and a no-retry rule for non-transient blocks before the first burst failure, not after a multi-day outage.

## Centralize Drift-Prone Config — the Second Hardcoded Copy IS the Bug (2026-07-09)
**Learning**: When the same configuration value — a schedule slot, a threshold, an enum→behaviour mapping — is hardcoded in more than one location, changing it means finding every copy and you WILL miss one. The miss is silent and downstream: a validator, a dashboard, or a doc keeps asserting the OLD value and emits a false alert or a wrong render that looks like a brand-new bug. The tell: you move a value in file A and then chase the identical literal into B, C, D. **The moment you patch the same literal a SECOND time, stop and extract it** — one config file plus a small accessor exposing read helpers and a `verify` that asserts consistency (every reference resolves, no conflicts or duplicate roles), then wire ALL consumers: planners, validators, dashboards, AND docs. Run `verify` as a preflight so drift fails loudly instead of silently. Corollary: separate the low-level "grid of every valid value" (changes rarely) from "which value is active/assigned now" (changes often); centralize the volatile assignment, keep the grid as its own constant, and have `verify` assert assignment ⊆ grid — retired values stay in the grid so old records still resolve but drop out of the active assignment. Stack-agnostic.
**Apply when**: Any project with scheduling, feature-flag, threshold, or slot surfaces. Trigger on the second edit of the same literal — that is the extraction signal.

## A Fix Recorded in One Consumer of Shared Infra Doesn't Reach the Others (2026-07-14)
**Learning**: When several projects each integrate the same shared internal service (an auth hub, an API gateway, an internal platform), each consumer typically hand-rolls its own client. A gotcha discovered and fixed in one consumer — an endpoint needing a specific header+body shape, a silent failure mode — lives only in that project's fix log. The next consumer to integrate, or a rewrite of an existing one, re-derives the client from the service's API surface and faithfully reintroduces the identical bug; the same defect recurred across three consumers this way. Reading the sibling's **code** is not enough: code shows what it does, not what it learned, and a naive reimplementation looks correct precisely because it matches the API docs — the failure it prevents is invisible in the source. These bugs are especially durable when the failure is silent (the call resolves, the caller proceeds, only the side effect is missing). **Before porting or reimplementing a client for shared infra, grep the sibling consumers' recorded fixes and memory, not just their source** — the sibling's fix log IS the spec. The durable remedy is extracting the client into one shared package so a fix reaches every consumer at once; until that exists, treat "N projects hand-roll this client" as a standing defect-propagation risk and record each gotcha where the next integrator will actually look.
**Apply when**: Integrating, porting, or rewriting a client for an internal shared service other projects already consume — read their fix logs first. If the same client is hand-rolled in 3+ places, propose extracting a shared package.

## The Local Pre-Commit Gate Must Be Command-Identical to the Deploy Build, Not a Correlating Subset (2026-07-18)
**Learning**: A pre-commit ritual that runs a linter plus a single package's type-check spot-check (`--noEmit` on one workspace) can pass while the production build fails. A local gate that runs a *subset which merely correlates with* the deploy gate will eventually green-light a defect the real build would have caught. ## Mirrors of External State Must Carry Provenance (2026-07-26)

**Learning**: A value stored in a repo that describes something OUTSIDE it — a deployed image tag, a vendor's hardware class, a price, an FX rate, "what artifacts exist on disk" — is a MIRROR, not a fact. With no record of when it was last confirmed, a stale mirror is indistinguishable from a correct one, so confidence stays high while truth drifts. Three separate wrong conclusions in one session traced to this: a config naming a deployed version two minors behind reality, a plan citing an external discussion thread nobody had opened (it was about something else), and an analysis of a 0%-failure bucket that was really failures being overwritten in place by the producer's retry. What compounds it: a test asserting a mirrored value's CONTENT turns staleness into green CI — a test hardcoding the same literal as the config it checks agrees with that config forever and actively endorses the drift. Mitigations, in leverage order: (1) give every mirrored value an entry recording what it mirrors, where the truth lives, HOW to re-check it, and when it was last confirmed, plus a test that FAILS once overdue — the test failing with no code change is the feature; (2) assert a mirror's SHAPE or that it matches its declared source, never its literal content; (3) treat a citation as a promise until fetched — quote the source's title or a line from it, never a bare issue number; (4) before interpreting a population of artifacts, find the producer's WRITE PATH — if it can overwrite, retry, or clean up in place, the survivors are a filtered sample and any rate computed from them is meaningless, with a 0% or 100% bucket as the tell; (5) before believing a metric correlates with some dimension of the input, re-measure the SAME artifact along that dimension — if the number does not move, the metric is clean and the effect is real or selection.

**Apply when**: storing any externally-owned value in config (deployed versions, vendor hardware, pricing, rates); writing a test that touches such a value; citing an external issue/discussion in a plan; computing failure rates or comparisons over artifacts a pipeline produced.

## Browser Captures for External Delivery Must Be Stripped of Automation Chrome (2026-08-15)

**Learning**: Any browser capture that leaves the team — reviewer demos, submission evidence, marketing, docs, customer-facing bug repros — must show the product and nothing else. Automation leaves fingerprints in the frame: launching a browser as root silently adds a sandbox-disabling flag, and the browser paints an "unsupported command-line flag" warning banner across the window — directly above the product being judged. A capture API that records only the page viewport excludes the banner by luck, not design; a window-level grab, an OS screen recorder, or a different capture library lands it in the file. Concretely: suppress automation infobars (`--disable-infobars`, `--test-type`, or run non-root so the flag is never added), avoid recording browser chrome at all, and close notification/consent/update overlays before filming. Then verify the frame, not the theory: extract a frame from the finished file and look at it — "this API records the page, not the window" is a claim about a library's behaviour, the same class of assumption that fails everywhere else.

**Apply when**: Producing any recording or screenshot of a browser for an audience outside the team. The prompt: "if a reviewer paused on any frame, would they see only the product?"

## A Green Suite That Never Ran the Line (2026-08-15)

**Learning**: A raw SQL fragment's TypeScript generic (`sql<Date>`) is a compile-time assertion with zero runtime force — ORMs apply driver-value mapping only through column configuration, which raw aggregate fragments (min/max/sum over a timestamp) don't carry, so the value arrives as a string everywhere, dev included. The failure shipped because the code path was conditionally empty in every environment that gated it: no fixture seeded a row inside the query's time window, so the `.map` over the results never executed and the suite stayed green while production — where live data always populates the window — threw on first contact. Two rules fall out: (1) every raw aggregate over a mapped column gets the column's mapper explicitly (`.mapWith(column)`) or a runtime coercion, never a bare generic; (2) when adding a query with a data-dependent window, the regression test that matters is the one that seeds a row INSIDE the window — an endpoint test that passes against empty state proves only the empty branch.

**Apply when**: Writing raw SQL fragments in any ORM with driver-value mapping; reviewing "worked in dev, 500 in prod" faults; writing tests for endpoints whose payload sections are conditional on time-windowed data.

## A Collapsing Formatter Can Eat Your Regression Test's Control (2026-08-15)

**Learning**: When a regression test asserts on output DOWNSTREAM of a formatting layer that deduplicates or collapses repeats ("2 × <line>" roll-ups, uniq filters, pretty-printers), the layer can absorb exactly the defect the test was written to detect — the break-the-check control passes with the guard disabled, and the test proves nothing. Witnessed live: a digest's repeat-collapse merged two identical stale rows into one line, so a count-the-lines assertion could not see the duplication it targeted. Invert the assertion to the formatter's own tell (the "N ×" multiplier's absence), or assert upstream of the collapsing layer. Always run the disabled-guard control and be suspicious when it passes on the first try.

**Apply when**: Writing regression tests for dedup/filter/rollup behaviour anywhere the asserted surface passes through aggregation, collapsing, or pretty-printing before the assertion reads it.

## Third-Party Embeds Can Be Owner-Gated Per-Item — Bisect by Item Before Blaming Your Code (2026-06-02)
**Learning**: A third-party media embed (video, map, document viewer) that renders "unavailable" inside your iframe while the same item works at the provider's own URL is an item-level or origin-level *permission*, not a CSP, browser, or code fault — and the tell is that a different item from a different owner embeds fine on the identical page. Provider-side gates are per-item and largely invisible to the embedder: embedding disabled by the owner, unlisted/private status, audience/age designations that silently strip embed features, region blocks, and origin gates that behave differently on `http://localhost` than on an HTTPS origin. Diagnose in this order, all free: (1) open the item at the provider's own URL on the same device — if it works there, your code is not the cause; (2) swap in a known-good item from a different owner — if that works, the gate is item-level and unfixable from your side; (3) only then test an HTTPS origin (a tunnel to localhost is enough) to separate an origin gate from an item gate. Do NOT invent a provider setting to explain the behaviour — record what you observed and what you swapped, since embedders cannot see the owner's configuration.
**Apply when**: Any third-party embed that shows "unavailable" in an iframe but works at the provider's own URL. Bisect by item and by origin before touching CSP, sandbox attributes, or player parameters.

## A Deterministic Guard That Only Speaks One Language Silently Stops Guarding (2026-08-15)
**Learning**: A regex/keyword safety net over user-generated text (force-review triggers, abuse filters, escalation nets) written in English-only stops guarding the moment a real audience arrives — and it fails silent: the guarded system keeps running, the net keeps passing everything, and the miss surfaces as a public incident, not an error. The failure compounds with an LLM judge in the same lane: a polite factual correction ("Eso no es correcto") reads as neither complaint nor question to the model, so BOTH nets pass it. Fixes: (1) name the semantic category explicitly in the LLM's instructions ("claims the post is wrong/mislabeled/AI-generated/fake, in any language") — the model handles languages the regex will never list; (2) extend the deterministic net with the audiences' actual languages, accepting over-match (cost: one human glance) over miss (cost: the brand autonomously defending a wrong post); (3) mind JS \b: it is ASCII-word-based, so accented phrases ("não é") need substring matching, not word boundaries. Test both directions: claims force review AND plain praise in the same languages does not.
**Apply when**: Any deterministic text-trigger list over user content in a product with a non-English (or even potentially non-English) audience; any auto-send/auto-action lane gated by keyword nets.

## A Uniqueness Check Is Only as Global as Its Lock Key (2026-08-15)
**Learning**: A check-then-insert guarded by an application lock prevents only the races the LOCK KEY covers — a per-tenant lock closes same-tenant races and is invisible to cross-tenant ones, which are precisely the ones a multi-tenant product must fear (two customers claiming the same external account). The only guard that holds at every scope is the database constraint (unique index); the app-level check remains as the friendly-error path. The second-order trap: the comment above the lock described the covered race with complete accuracy — and correct prose above an insufficient guard reads as a settled question, which is exactly why nobody looked further. When auditing concurrency guards, ask "what is the lock KEYED on?" and enumerate the actors who don't share that key; also expect fixtures to break honestly when the constraint lands (shared literal ids across test tenants are the index working).
**Apply when**: Any check-then-act on a uniqueness invariant in a multi-tenant system; any review of code whose safety comment reads convincingly.

## A Loader That Enumerates Directories Must Assert the Marker File, Not Just the Directory (2026-08-16)

**Learning**: Any build/deploy step that discovers units by listing directories — plugins, skills, modules, migrations — must assert the marker file that DEFINES a valid unit before it copies or counts, because a directory is cheap to create by accident and a half-built unit looks identical to a real one from the outside. Observed: a build script whose copy loop tested only "is this a directory" and incremented its own counter, while a later registry loop correctly required the unit's manifest file and skipped anything lacking it. The result of leaving a scratch directory in the tree was a shipped artifact containing a unit with no manifest, a reported count one higher than the registry it published, and no error anywhere — the two loops disagreed silently because only one of them encoded what "a unit" means. The asymmetry is the tell: when one pass validates and another doesn't, the unvalidated pass defines what actually ships. Fix both loops to the same predicate, and prefer failing loudly on a malformed unit over skipping it, since a silent skip and a silent copy are the same bug wearing different clothes.

**Apply when**: Writing or reviewing any directory-enumerating build, packaging, or deploy step; also whenever a scratch/draft directory is created inside a tree that a build script walks — the draft becomes shippable output the moment it exists.

## A Plausible API Name Hardens Into a Premise the Moment It Is Written Down (2026-08-16)

**Learning**: An API scope/endpoint name that follows a vendor's real naming style (matching the shape of genuine neighboring names) reads as obviously real and gets passed between sessions, briefs and application drafts as fact — and every downstream reader inherits it as a premise, planning retirements and adapter work against an API that does not exist. The whole plan survived several capable reviewers because each verified everything DOWNSTREAM of the name (sequencing gates, demand evidence, structural claims) while the name itself entered unverified upstream. Rule: before any external API name enters ANY document — a brief, a design doc, an application draft — check it against the vendor's own catalogue (scopes reference, product list, docs URL resolving), and record the check. Corollary: absence from public docs does not disprove a closed programme — the follow-up is a written vendor question, not an assumption in either direction.

**Apply when**: Writing anything that names a third-party scope, endpoint, or product; inheriting a brief that names one; reviewing plans whose feasibility rests on a named external capability.

## A Correct-Looking 200 in the Wrong Content Type Defeats Every Standard Check (2026-08-16)

**Learning**: An SPA fallback (or any catch-all route) answering infrastructure paths — /robots.txt, /sitemap.xml, /.well-known/* — returns 200 text/html for requests that needed machine-readable content, and every standard check passes: nothing errors, nothing 404s, the deploy reports success, monitoring sees healthy status codes. The consumer (a crawler, a verifier) silently parses a web page as an empty rules file. The durable test shape: don't assert the route exists or returns 200 — assert the response is NOT HTML (or IS the expected content type), per host, because the defect's whole shape was a correct-looking status with the wrong body. Serve such paths AHEAD of every redirect; a 301 into a catch-all is how the lie starts. Same family as "silence is not success": here, success-shaped responses are not success either.

**Apply when**: Any worker/server with an SPA fallback or hostname redirects; any test of machine-consumed paths; diagnosing "the crawler/verifier ignores our file" reports.

## Approval Does Not Travel Between Sessions (2026-08-16)

**Learning**: In multi-agent work, a user's approval is scoped to the session that asked. Relaying "the user said yes" from one session to another as authorization is permission laundering in its politest form: a decision made in one context becomes a licence in another, and neither side ever sees the seam. The benign version (both sessions independently got the same answer) is indistinguishable at relay time from the harmful one (the answer covered different work than the receiver thinks). Rule: each session asks its own user question for its own decisions; a relayed approval is INFORMATION ("expect them to say yes"), never AUTHORIZATION. The receiving side's correct behaviour is to decline to act on the relay and close the decision in its own session.

**Apply when**: Any cross-session/agent handoff involving a pending user decision; writing coordination messages that mention what the user approved.

## Recording a Human's Screen Interaction Needs Xvfb + a Real Window Manager, Not Just a Display (2026-08-18)

**Learning**: Recording (or VNC-sharing) a browser for a "the human must genuinely interact, not a script" compliance video failed through three distinct, non-obvious layers before working: (1) capturing a specific window by X11 window-id on a Wayland-backed display (e.g. WSLg's default) never sees native popups (a `<select>` dropdown's option list, context menus) at all — they render as a SEPARATE override-redirect window outside that window's own composited buffer, invisible to window-id grabs and to x11vnc (which refuses outright on a Wayland display server — it needs a real X server, not Xwayland-over-Wayland). (2) Switching to a genuine X server (`Xvfb :N`) fixes visibility of the popup's WINDOW but not its CONTENT — Chrome auto-disables GPU compositing on a GPU-less Xvfb, and its software-bitmap-presenter path silently fails to paint override-redirect popup surfaces, producing a popup that opens at the right size/position but renders BLANK — confirmed by burst-capturing frames across a live click rather than trusting a single screenshot. (3) The actual fix was a THIRD layer: Xvfb alone runs with no window manager, and Chrome's popup-window handling depends on WM semantics being present even for override-redirect windows it's nominally exempt from; installing and running a trivial WM (`fluxbox`) alongside Xvfb made the popup paint correctly. The full working stack for "human clicks, everything including transient popups is visible/recordable": `Xvfb :N` (real X server) + a lightweight WM (`fluxbox`) running on it + `x11vnc -display :N -localhost` (must run with `WAYLAND_DISPLAY` unset in its environment even when targeting the Xvfb display — x11vnc's Wayland detection checks the env var, not the display it's told to serve) + `websockify` for a browser-based viewer + plain `ffmpeg -f x11grab` (whole-display capture, not window-id-targeted) for the recording. Each layer's failure was silent or misleading on its own — the tell each time was capturing evidence (burst frames, log greps) rather than trusting that "the display exists" or "the window opened" meant the content was actually there.

**Apply when**: Any task needs to record, or share a live view of, a human operating a real (non-scripted) browser session where native OS-level popups matter — compliance/audit demo videos, "show a human passing a captcha/2FA" flows, screen-recording rehearsals. Build the full stack (Xvfb + WM + VNC + plain x11grab) from the start rather than discovering each missing layer by watching a symptom.

**Learning**: Launching a GUI application (Chrome) from a background shell command produced two distinct SILENT failures while setting up a recording pipeline, neither surfaced by the launch command's own exit status. ## The Authoritative Row and the Data-Bearing Row Can Be Different Rows (2026-08-19)

**Learning**: Before deleting a duplicate record, check what data exists ONLY on the row you are about to delete — the row that looks authoritative by every obvious signal (real lineage, correct provenance, the write you trust) may not be the row holding the asset pointers or media references. Evidence: fifteen duplicate-record groups in a production ledger, each representing one real item recorded twice — one row written by the current system with true lineage, one row imported by a legacy pipeline. The obvious cleanup is keep-the-lineage, drop-the-import. But the import rows held ALL fifteen thumbnails and the lineage rows held ZERO. The delete would have traded a duplicate listing for fifteen blank tiles, silently — nothing errors, and the surviving row still looks correct by every field you would think to inspect. This generalises because duplicates arise from two different writers, and different writers populate different columns; the split is the normal case, not the exception. The rule: diff the columns across the group and ask "what is non-null ONLY on the row I am dropping?" Prefer an order that heals first — let the repair/refresh path restore what the duplicate uniquely holds, VERIFY it landed, then delete. Delete-first is unrecoverable, and the verification step is the one people skip because the repair "should" have worked.

**Apply when**: Writing or reviewing any de-duplication cleanup, data migration that collapses records, or "tidy up the duplicates" task.

## A Guard Enforced In Every Caller Is a Convention, Not a Property (2026-08-19)

**Learning**: When a safety rule (a cutover flag, a kill switch, a permission check) is enforced by every CALLER rather than at the seam those callers share, the guarantee is "every author remembered" — that is a convention, not a property, and the exception is always a manual, off-schedule tool nobody thinks of as part of the system. Evidence: during one migration cutover, two independent legacy codebases were audited for reachable native-publishing paths. In both, every scheduled/cron path was correctly gated. In both, exactly one manual script — written for a one-off demo or audit recording, not on any schedule, called by nothing — reached a live publish API with no guard at all. One of them additionally read its input straight from a still-populated pending queue. The adapters themselves carried no awareness of the rule in either codebase. Scheduled paths get audited because they run on their own; manual tools are invisible to that audit precisely because nothing triggers them — until a human does, usually during exactly the kind of demo or debugging session that a migration creates. The rule: put the guard at the narrowest seam every path crosses — the function that makes the network write, not the CLI entry point, so a future direct import is covered too. Then verify by EXECUTION, not compilation: import the module with the flag set and call the guarded function, expecting the refusal — a syntax/compile check proves nothing about whether an import resolves or a guard fires. Where the seam cannot hold the guard, add a mechanical check (grep for files calling the write function that do NOT import the guard module) so the convention becomes a test.

**Apply when**: Auditing a system for reachable paths during a migration or cutover; adding a kill switch or feature flag that must hold everywhere; reviewing "we gated all the publish paths" claims.

## A Borrowed Terminal State Carries Semantics You Did Not Ask For (2026-08-19)

**Learning**: When you need a record to stop being processed, reaching for an existing terminal status because it happens to remove the row from a query is how you inherit that status's OTHER meanings — and the one you did not read is usually the one that fires. Evidence, three instances in a single evening across two engineers on one codebase: (1) a de-duplication guard scoped to one key was assumed to mean "one real object has one key" — it did not, the same real object could arrive under a second key from a different import path, so the guard silently admitted duplicates; (2) a never-repeat guard was wired into a new intake path by reusing an existing helper that wrote its entries as PERMANENT, correct for its original caller — on the new path it would have permanently banned every item on first sight, exhausting a rotating content pool within two weeks, converting a duplicate-content bug into a total outage; (3) a record whose external identifier had become unresolvable needed to stop being retried forever — the obvious fix set its status to "failed", the only terminal state that removed it from the sweep's queries, but the publish path atomically RE-CLAIMS any record in "failed" state with an expired lease, so "failed" did not mean "stop", it meant "claim me and retry"; ten records, all verified genuinely live on the platform, would have been re-published. Each was invisible until someone read what the existing path actually DOES rather than what its name implies, and in each case the reviewer who caught it was not the author. The rule: before reusing a status, helper or code path for a new purpose, enumerate every consumer that reads it and what each infers. When no existing state means what you need, add one (a dedicated nullable column costs a migration and is honest) rather than overloading a state that means something adjacent. And prefer a reviewer who did not write it — all three were caught by the other person.

**Apply when**: Reusing an existing status/enum value for a new situation; wiring an existing guard or helper into a new call path; any change whose implementation is "set it to the state that makes it disappear from the query".
