## Drizzle Migration Operations Across Fresh and Existing DBs (2026-03-19)
**Learning**: Three rules together govern safe Drizzle migrations: (1) **Versioned for persistent, push for ephemeral** — `db:migrate` for production and any persistent DB; `drizzle-kit push` only for throwaway DBs (CI test runs, local dev reset). Mixing on the same persistent DB causes drift, since push doesn't track history. (2) **Seed the journal when transitioning** — Drizzle's `migrate()` stores history in schema `drizzle` table `__drizzle_migrations`; when switching from push to versioned, create the schema/table and insert a row for the baseline migration so the migrator's `created_at` comparison knows what's already applied. Deploy pipelines should auto-stamp the baseline before running `db:migrate` on push-originated DBs. (3) **Guard fixup scripts against fresh DBs** — `ALTER TABLE` fixups crash when the base table doesn't exist yet; always wrap in `SELECT 1 FROM information_schema.tables WHERE table_name='X'` so the fixup only runs when the table is present.
**Apply when**: Any project transitioning from drizzle-kit push to versioned migrations, or operating Drizzle migrations across both fresh and existing databases.

## Supabase RLS Must Use JWT Claims, Wrapped in `select` (2026-03-28, corrected 2026-10-02)
**Learning**: An RLS policy that resolves the tenant from a profiles table — `WHERE tenant_id = (SELECT tenant_id FROM profiles WHERE id = auth.uid())` — adds a table read (itself RLS-checked) to every policy evaluation. Store `tenant_id` and `role` as custom JWT claims via a Supabase Auth hook and compare against the claim instead, and wrap the call in a `select` so the planner runs it once per statement as an initPlan: `tenant_id = (select auth.jwt() -> 'app_metadata' ->> 'tenant_id')` (cast to the column type). The unwrapped `auth.jwt() -> ...` form is still evaluated per row; the same wrapping applies to `auth.uid()` and to security-definer helpers whose result does not depend on the row. Read claims from `app_metadata` (service-role-writable only), never `user_metadata` (user-editable). A JWT is a snapshot: a changed claim takes effect only when the token refreshes. Mark helper functions `STABLE`, not `IMMUTABLE`, to avoid stale results within a transaction.
**Apply when**: Writing Supabase RLS policies for any multi-tenant app. JWT claims over table lookups, and every `auth.*()` / helper call wrapped in `(select ...)`.

## Supabase + Drizzle Dual-Access Pattern for Complex Apps (2026-03-28)
**Learning**: For apps with 20+ tables and complex queries (joins, CTEs, aggregations, transactions), use BOTH Supabase JS client and Drizzle ORM. Supabase JS for: auth, realtime, storage, and simple client-side CRUD (benefits from RLS). Drizzle for: server-side queries, reports, transactions, and complex joins (bypasses RLS, so enforce auth in application code). Connect Drizzle via Supabase's connection pooler URL (port 6543, transaction mode), not direct connections (which exhaust limits from serverless functions). Transaction mode does not support prepared statements — create the Drizzle/postgres client with `prepare: false`.
**Apply when**: Starting any Supabase project with more than 15 tables or complex reporting requirements.

## LibreOffice in Docker Needs a Persistent Daemon (2026-03-28)
**Learning**: LibreOffice headless Docker images are 400MB-1.2GB. Each conversion spawns a fresh `soffice` process (1-3 second cold start, 200-500MB memory spike). For production: use Gotenberg (Go microservice wrapping LibreOffice with queuing) or unoserver (keeps LibreOffice as a persistent daemon). Never convert documents synchronously in an API request — always queue conversions. Budget for a small dedicated conversion container — free-tier compute is insufficient for the memory profile.
**Apply when**: Adding document conversion to any project. Never put LibreOffice on a free-tier container.

## Free-Tier Limits Change Without Notice — Verify Against Project Volume at Review Time (2026-03-29)
**Learning**: Cloud API providers silently change free tier limits without announcements. Always verify current limits against the actual API pricing page at architecture review time, never trust cached or remembered values, and model the project's real volume against the ceiling before committing. Secondary models or tiers may become the practical workhorse when primary tier limits drop. Voice products are the sharpest case: cloud TTS free tiers have monthly character ceilings that are easy to exceed, so model monthly character volume first, then choose between (a) staying within a verified free tier, (b) committing to a paid plan, or (c) self-hosting an open-weights TTS. Unofficial wrappers around vendor browser endpoints periodically appear in the npm/pip ecosystem promising "unlimited" access — they are unauthorized, fragile, and TOS-grey; treat them as throwaway prototyping tools, not production dependencies. Specific package names belong in stack guides, not in this evergreen learning — they decay rapidly when the underlying vendor endpoint changes.
**Apply when**: Evaluating any cloud API free tier during architecture review or probe, and selecting a TTS provider for any voice-enabled project.

## ML Library Language Ecosystem Compatibility (2026-03-29)
**Learning**: Python ML libraries (speech processing, embeddings, computer vision) often have no JavaScript/WebView implementation path. When a blueprint specifies an ML model for on-device mobile use in a hybrid app, verify the language ecosystem compatibility first. ONNX export + native runtime is the bridge, but adds significant complexity vs. a server-side approach.
**Apply when**: any blueprint or architecture that specifies ML inference on a mobile/hybrid client — verify the model has a JS-compatible runtime or plan for server-side inference.

## Scale-to-Zero Pays Only for Bursty Workloads — a Warmer or an Always-On Consumer Inverts It (2026-03-29 → 2026-07-19)
**Learning**: "Default to serverless/scale-to-zero" assumes bursty traffic where sleeping pays. Two signals say the assumption has failed. (1) Cold starts: a scale-to-zero serverless database (300-500ms cold start) combined with scale-to-zero compute containers (2-5s at min-instances=0) produces first-request latencies of 4-9 seconds. The free-tier answer is a health-check cron every 4 minutes during business hours — but a warming cron IS an always-on consumer: it converts the free tier's compute-hour allowance into a ~300h/month burn and removes the sleeping that made serverless cheap. Reach for it only when cold-start latency is the binding constraint AND the tier is metered on requests rather than compute hours. (2) Any always-on component (a per-minute cron or queue consumer): the instance never sleeps, serverless pricing loses to a small flat-rate managed instance, and free-tier compute hours burn out in days. Either way, needing a warmer means the workload is no longer bursty: pick a flat-price provider in the required region and keep the exit cheap — use the DB as plain vanilla Postgres (no provider-specific features), reach it through a connection-string indirection layer, and keep nightly logical dumps restore-drilled. Then a provider swap is ~30 minutes and "too late to switch" never happens.
**Apply when**: Deploying any app on serverless DB + serverless compute where scale-to-zero is enabled; choosing a Postgres host for a stack with an always-on consumer; re-checking any "serverless DB by default" recommendation.

## iframe Sandbox Defense-in-Depth for AI-Generated Content (2026-03-29)
**Learning**: `sandbox="allow-scripts"` without `allow-same-origin` prevents the classic sandbox escape, but is insufficient alone for AI-generated HTML. LLM output injection (OWASP LLM05:2025) means the generated content itself is the attack surface. Required layers: (1) serve from separate origin, (2) CSP headers `connect-src 'none'` to block exfiltration, (3) server-side DOMPurify sanitization before storage, (4) content safety scan before first render (not async post-publish).
**Apply when**: Any platform serving AI-generated content in sandboxed iframes.

## Auth Libraries With Flat User Models Need Custom Sub-Profile Tables (2026-03-29)
**Learning**: The general rule is "auth library owns identity, don't create parallel user tables" (see `Auth Library Territory` in global-patterns.md). The exception: auth libraries with flat data models have no native support for hierarchical relationships like parent-child accounts. Organization plugins are for SaaS tenancy, not family structures. The correct pattern: auth library handles primary user auth only; subordinate profiles (children, sub-accounts) use a first-party table with scoped session tokens managed entirely by application code (Netflix, Disney+, Roblox pattern).
**Apply when**: Any project using an auth library that needs hierarchical user relationships (parent-child, manager-employee, guardian-ward).

## Scaling Runway Is a Design Question — /probe Owns the Future State (2026-04-02 — not yet in the probe SKILL as of 2026-10-02)
**Learning**: "Does this design scale?" is an architecture question; "can the current deployment take launch load?" is an ops question. /press scores the second (its Scalability dimension, current state). The first belongs in /probe as a "Scaling Runway" section assessing: (1) stateless request handling, (2) database scaling path (pooling → replicas → partitioning → sharding), (3) external dependency scaling (AI provider, CDN, queue), (4) what user count triggers each scaling tier. Present as a table: user range → required change → effort level. A scaling ceiling is a design flaw, not a deployment gap.
**Apply when**: Running `/probe` on any blueprint or architecture — include the runway table; the SKILL does not list it yet.

## Fraud/Risk Fields Belong on the Event Table, Not the Entity Table (2026-04-25)
**Learning**: When fraud-detection fields (risk score, fraud flag) are derived from per-submission signals (IP, device, timestamp, fingerprint), they must live on the same table as those signals — not on the parent entity. Placing them on the entity when the source data is on the event forces either expensive joins or denormalization drift. The computation belongs where the evidence lives.
**Apply when**: Any blueprint with fraud scoring, risk flagging, or audit fields — verify the scored fields and their source signals are co-located on the same table.

## Cloud Task Queues Should Use Platform IAM Tokens, Not Shared Secrets (2026-04-25)
**Learning**: Using a shared-secret header (e.g., `X-Internal-Secret`) for cloud-task-queue → service authentication is an anti-pattern: secrets rotate manually, they can leak via logs, and they don't integrate with the platform's IAM auditing. The correct pattern is short-lived signed tokens — the task queue attaches a token from a dedicated service identity, and the receiving endpoint verifies it automatically when IAM-protected. Examples: GCP Cloud Tasks → Cloud Run uses `oidcToken: { serviceAccountEmail, audience: ENDPOINT_URL }`; AWS SQS → Lambda uses IAM execution roles; Azure Service Bus → Functions uses managed identity.
**Apply when**: Any architecture using a cloud task queue to invoke a service endpoint. Always specify platform-native IAM tokens; never use header-based shared secrets.

## In-Memory Rate Limiting Is Correct Only Under a Pinned Single Instance (2026-04-25, evolved 2026-10-02)
**Learning**: In-memory rate-limit middleware silently breaks when a service runs more than one instance — each instance maintains its own counter, so a client hitting multiple instances bypasses the limit by a factor of `max-instances`. On any auto-scaling platform (serverless containers, FaaS, managed compute) this is a Day 1 correctness issue, not a scaling concern to defer: back the middleware with a shared store (Redis, Memcached, DynamoDB). The only valid in-memory case is a deployment pinned to exactly one instance, with that constraint written down and the shared store named as a precondition of horizontal scale (the stack guide's Day-1 single-box topology).
**Apply when**: Any blueprint with rate limiting. On auto-scaling platforms spec shared-store limiting; on a single box, verify the single-instance constraint is documented, and re-check the verdict whenever the deploy target changes.

## SMS Gateway OTP APIs May Reject Pre-Generated Codes From Auth Libraries (2026-04-25)
**Learning**: Some SMS gateways have their own OTP generation APIs and reject codes pre-generated by your auth library — the formats, character sets, or expiry semantics don't match. Two paths: (A) use the auth library's code generation + the gateway's plain SMS message API (e.g., `Your OTP is: ${code}`) — simplest and most reliable; (B) use the gateway's OTP API and implement a custom flow outside the auth library. Path A is strongly preferred unless carrier-grade delivery features (delivery receipts, network priority routing) are required.
**Apply when**: Integrating any auth library's phone OTP feature with a regional SMS gateway. Verify the gateway accepts pre-generated codes before committing to the auth library's native flow.

## Real-Time Default Should Be SSE; Managed Pub/Sub Is the Upgrade Tier (2026-05-10)
**Learning**: WebSocket pain ≠ real-time pain. Managed pub/sub services (Ably, Pusher) solve the *WebSocket* class of bugs (reconnection, presence, multi-region delivery), but the typical web-app workload — fanout notifications, live list updates, modest concurrency, no chat/multiplayer/financial-ticker requirements — does not need WebSockets at all. **Server-Sent Events (SSE)** — the W3C `text/event-stream` standard, browser-native via `EventSource`, with built-in auto-reconnect and `Last-Event-ID` resume — covers that workload with zero vendor lock-in, no cost, no SDK, plain HTTP that works through every proxy/CDN, and a server implementation that's a long-lived response writer most modern frameworks handle natively. Managed pub/sub's differentiated value props (built-in presence, durable history with replay, multi-region delivery guarantees, true bidirectional channels) only matter for a minority of projects. Default to SSE; reserve managed pub/sub for the upgrade tier when presence/history/multi-region is a genuine requirement. Mirrors the existing database tier pattern (commodity default, managed upgrade). One server-side caveat: SSE is awkward on platforms with long-lived-connection limits (some serverless container runtimes, edge workers) — projects deploying there should evaluate the managed tier earlier. Push notifications are a different decision: delivery while the app is closed or backgrounded needs platform-specific infrastructure (Firebase project, APNs key, device token storage) and can often wait for a post-launch sprint informed by real engagement data. Decide which of the two launch needs; do not conflate "real-time updates" with "push notifications".
**Apply when**: Reviewing or drafting a Pattern's real-time layer. Ask whether the workload is fanout-style (SSE) or presence/history-style (managed pub/sub). Don't auto-reach for a managed pub/sub service from reflex; the reflex usually conflates "I need real-time" with "I need WebSockets". Scoping real-time features for mobile or web apps.

## OAuth `state` Must Be Browser-Bound, Not Just Signed (2026-06-21)
**Learning**: A signed-and-unexpired OAuth `state` parameter is necessary but NOT sufficient for CSRF protection on the authorization-code callback. A purely cryptographic state proves "this server issued some state," not "this state belongs to the browser now completing the flow" — an attacker who obtains any valid state can replay it to fixate a session on a victim. Bind the state to the initiating browser: at login-redirect time set a short-lived `HttpOnly`/`Secure`/`SameSite` cookie carrying the same nonce; on callback require BOTH (a) the returned state validates (signature + expiry) AND (b) it matches the browser's cookie via a constant-time compare. Reject when the cookie is absent or mismatched — that is the exact case that catches a forged or cross-browser-replayed state — and delete the cookie on success. The same principle applies to any redirect-based handshake secured by a state/nonce round-trip.
**Apply when**: Reviewing or designing any OAuth2 / OIDC authorization-code flow, or any redirect-based callback secured by a `state`/nonce. Verify the state is bound to the browser (cookie or server-side session), not merely signed.

## Publish-Once Guarantees: the Ledger Key and Write Ordering Are Where They Break (2026-07-04)

**Learning**: Two defects recur in otherwise careful exactly-once designs for external side effects, both invisible until production: (1) a uniqueness key that omits the tenant dimension — e.g. (itemSlug, destination) without tenantId — turns cross-tenant slug reuse into a silently LOST action (ON CONFLICT DO NOTHING swallows it), worse than the duplicate it guards against; (2) writing the ledger row AFTER the external call means a crash between external success and ledger write duplicates on retry. The guarantee requires claim-before-side-effect: txn 1 inserts the row with status='in-progress' (ON CONFLICT DO NOTHING; no row returned ⇒ already claimed ⇒ no-op), the external call runs outside any transaction, txn 2 updates with the external id; stale in-progress rows reconcile via a verify/list-recent step. State the delivery model explicitly — "exactly-once against external HTTP does not exist; we run at-least-once drain + at-most-once side effect per claim" — or builders trust the wrong invariant.

**Apply when**: Reviewing any system that must perform an external side effect exactly once per logical item (payments, emails, posts, webhooks, provisioning). Check the uniqueness key for the tenant dimension and the ledger write ordering first. Companion entries: "A Transport Error Is Not a Publish Failure — Verify Against the Account, Defer What You Cannot Confirm" (pry-learnings.md), and gate (3) of "Standing Up a Social Media-Publishing Integration — Three Gates, In Order" (pry-learnings.md).

## Self-Hosted Single-Box Deployments Need a Resurrection Chain and Out-of-Band Detection (2026-07-04)

**Learning**: An application can be genuinely downtime-tolerant (durable queues, catch-up drains, upstream-native scheduling) and still suffer unbounded outages because the HOST layer was never specified. Five links, each defaulting to off: host-boot auto-start of the VM/runtime (e.g., Task Scheduler for WSL2), init system enabled inside it (systemd + container engine), the ingress tunnel installed as a host-level service so it survives VM restarts, container restart policies (unless-stopped), and a memory cap sized so the host never kills the VM. And every alert channel that originates from the box dies with it — a dead-man's switch (external service expecting a periodic ping) is one cron line and turns "discovered Monday" into "paged in minutes." Restore discipline for side-effecting systems: a restored dump forgets everything since the dump, so the restore runbook must reconcile against external ground truth (list-recent from the destination platforms) before the scheduler resumes, or the restore itself causes duplicate side effects; the encryption key file must be backed up separately from the dumps it protects.

**Apply when**: Any self-hosted or single-box deployment review. Walk the five-link chain, demand the dead-man's switch, and check the restore runbook for reconcile-before-resume and key/dump separation.

## Analytics-Consumed Fields Belong in Typed Columns; Self-Tuning Loops Need Fixed Horizons and Sample Gates (2026-07-04)

**Learning**: The hybrid storage pattern — raw external payloads in jsonb (schemas differ, fields deprecate), comparables promoted to typed NULLABLE columns — is load-bearing wherever aggregation happens: Postgres keeps no planner statistics on jsonb internals, percentile/median functions need typed columns, and nullable columns encode "not available ≠ zero" for free. For self-tuning loops fed by such metrics: record outcomes at fixed maturity horizons (e.g., 48h and 7d, horizon stored on the row) rather than "next day," compute baselines over rolling windows, and gate any automated rebalancing on a minimum sample count — medians over tiny samples thrash the system they steer.

**Apply when**: Reviewing metrics ingestion from external platforms or any learn/optimization loop; promote the group-by axes to columns and check horizon + sample-size discipline.

## A Missing Label Is Not a Maturity Status: Read the Changelog (2026-10-10)

**Learning**: Absence of a label is not a status. A product page with no beta badge does not mean generally available, and a summarizing fetch will report it as if it did. Before repeating a maturity claim (generally available, beta, deprecated), find the explicit release line in the product changelog or release notes and cite its date; check limits and quotas the same way, since a starting quota may be published nowhere. Treat a summarizer's status claim as unverified until the primary line has been read. This is "A Claim Hardens Into a Premise the Moment It Is Written Down — Relaying Is Asserting" (`global-patterns.md`) applied to vendor maturity.

**Apply when**: Checking a vendor product's maturity, limits or pricing through a summarizing fetch or search before building on it.

## Swapping an HTTP-and-Secret Integration for a Platform Binding Changes the Wiring Surface (2026-10-10)

**Learning**: A platform binding is not a drop-in for an environment-variable API key. Code shared between a Node runtime and an edge runtime reads configuration from the process environment, where a binding never appears, so the binding has to be threaded from every handler that can reach the call, in every deployed worker. Size the swap by counting the call paths that reach the integration, not the call sites: a change that looks like two call sites can touch every entry point. The mechanism is recorded in `stack-guide.md` (Key Learnings → Cloudflare Workers, and Cloudflare Email Service → "A binding is not an environment variable"); this entry is the estimating rule.

**Apply when**: Estimating or planning a move from an HTTP API with a secret to a runtime-provided binding, especially in code shared across runtimes.

## Capture-Heavy AI Products: Free Instant Capture, Cheap Classification, Expensive Generation On Demand (2026-03-21 → 2026-03-29)
<!-- relocated from global-patterns.md by /purge, 2026-10-11 — sharpens one art, not cross-cutting -->

**Learning**: For an AI product with high-frequency input, split processing into layers with different cost profiles: **free capture → cheap classification → expensive generation only on demand**. Most interactions touch only the cheap layers; the expensive one fires when the user explicitly asks. This architecture decision IS the business decision: it is what makes the product viable for a solo founder. Four disciplines follow. (1) **Capture is instant and offline-first.** Capture must feel instant (<200ms), so heavy work (LLM classification, theme assignment, media pre-generation) fires AFTER the response is sent: don't await, use `promise.catch(() => {})`, and let the user see results on next view. When the core use case happens with no connectivity (commute, underground, spotty signal), offline-first is the difference between the product working and not working, and sync must be automatic: a capture tool exists to reduce cognitive load, and requiring the user to remember to sync defeats it. (2) **Modes are a volume dial, not separate machines.** When the product has several interaction "modes", check whether they are different pipelines or different amounts of the same processing. Usually one engine serves all of them, with the mode injected as context into one system prompt, from zero AI involvement (quick action) to full (open dialogue with history). Prefer one adaptive system over N specialised pipelines when the variation is in degree, not kind. (3) **Persist the expensive tier on first generate.** Store the rendered output (base64 in a column, or a jsonb map keyed by content) and serve from storage on every replay; never generate the same input twice. Learned from TTS, typically the largest scaling cost in voice-first products (often ~50% of total infra: model it separately and find the tier boundary where it dominates). (4) **Stream when latency matters.** Full synthesis adds 3–5s for long content; chunk streaming over a WebSocket with client-side scheduling starts playback in ~200–500ms. Persistence kills cost; streaming kills wait; opt-in playback is additionally a UX win.

**Apply when**: Designing any AI-powered product with high input frequency and heavy processing: settle the cost model, the offline and sync behaviour, the one-engine-or-many question, the persistence layer and the streaming-vs-blocking call on day one.

## Single-Use Refresh Tokens Race Under Concurrent Processes (2026-04-26)
<!-- relocated from global-patterns.md by /purge, 2026-10-11 — sharpens one art, not cross-cutting -->
**Learning**: When several processes share one OAuth credential and the provider issues *single-use* (rotating) refresh tokens, simultaneous expiry triggers a race: each process refreshes with the same refresh token, the first wins, the rest get `invalid_grant` and crash. The durable client-side fix is a **cross-process lock on the credential write** — refresh under a lock, re-read fresh inside it, and preserve the existing refresh token if the provider's response omits one (RFC 6749 §6). A proactive scheduled-refresher is a lighter mitigation, but if you build one, mind three traps: (1) **scheduled, not polling** — sleep until `expiresAt - margin`, refresh once, recompute; (2) **the refresher races itself** — serialize bursts via non-blocking `flock -n`, exit on lock loss; (3) **clock-skew on suspend** — re-read `expiresAt` on every wake.
**Apply when**: Designing or reviewing any multi-process system that shares a rotating OAuth credential. Agent harnesses with concurrent subagent fan-out hit this exact race and now handle it internally with a cross-process credential lock — the lesson applies to your own SDK integrations, not to the harness.

## Public Static API From Private Source — Split Private Builder + Public Mirror, One-Way Deploy-Key Sync (2026-06-28)
<!-- relocated from global-patterns.md by /purge, 2026-10-11 — sharpens one art, not cross-cutting -->
**Learning**: To expose a public, keyless, CDN-served static-data API while keeping the build logic, fallback strategy, and raw inputs private, one repo cannot do it — public static hosts that serve straight from a VCS only serve *public* repositories, so a private repo has no public path. The pattern is two repos: a **private source repo** (builder, source registry, raw landing zone, automation) and a **public mirror repo** holding only the consumer surface (the data, its schemas, a discovery catalog, the long-form archive). The build runs in private and syncs the allow-listed public paths into the mirror over a **write-scoped deploy key**. The path allow-list *is* the security boundary — it must be an explicit include-list in one script, never an exclude-list, so a new private artifact is private by default. Provenance (which upstream sources contributed) stays public because it is what makes the data trustworthy and is often required by source-attribution terms; only the *method* is hidden.
**Apply when**: You want a public dataset/API but must keep build internals, competitive logic, or raw third-party payloads private. Use a private builder + public mirror, sync one-way via a write-scoped deploy key for the high-frequency path and a separate narrowly-scoped token only where an API (e.g. release uploads) genuinely needs it, and make the public surface an explicit include-list in one script that doubles as the audited public/private boundary.

## Time-Series File Archives — Partition by Effective Date + Dedupe, Not Ingest Date (2026-06-28)
<!-- relocated from global-patterns.md by /purge, 2026-10-11 — sharpens one art, not cross-cutting -->
**Learning**: A file-based, append-only time-series archive (one shard per day in a VCS or object store, rebuilt on a schedule) duplicates data badly if it partitions by *ingest/build date* while each record carries its own *effective date*. Slow-moving or carried-forward values (a weekend rate, a policy figure unchanged for a year) get re-emitted into every build's partition, so a downstream "all values for entity X" query returns N copies per effective date and the cold-tier roll-up accumulates duplicates without bound. The fix is to partition by each record's **own effective date** and make each partition file idempotent: on write, merge with what is there, dedupe on the natural key (date, entity, field) with the freshest build winning, and emit sorted. Then a value re-observed across many runs is recorded exactly once, an unchanged day rewrites byte-identical content (so the VCS sees no diff), and re-runs are safe. The row *count* stays bounded by distinct observations, not by the number of builds — which is the property to assert in a test.
**Apply when**: Building any file/VCS-based time-series archive that rebuilds on a schedule and whose records have an effective date distinct from the ingest date. Partition by effective date, dedupe on the natural key per partition, and verify idempotency by asserting the total row count is stable across repeated rebuilds.

## LLM Cost Capture Is Four-Dimensional (2026-07-04)
<!-- relocated from global-patterns.md by /purge, 2026-10-11 — sharpens one art, not cross-cutting -->
**Learning**: Per-call cost actuals computed as input×rate + output×rate misprice every cached call: cache reads bill at roughly a tenth of the input rate, cache writes at a premium over it, and the input-token count excludes the cached prefix. Any spend ledger fed by LLM calls must price all four usage fields at their distinct rates, store the model ID plus a rate-effective-date per entry (intro pricing windows and quarterly model turnover corrupt historical entries otherwise), persist the provider request id for tracing, and verify caching actually engages (cache-read tokens > 0) since prefixes below the model's minimum cacheable length silently don't cache.
**Apply when**: Any product metering LLM spend per tenant, feature, or item — design the ledger schema around the full usage object before the first call is billed.

## A Platform's Terms Decide the Integration's Shape — Compliant Surface, Credential Model, Whose Meter (2026-09-11)
<!-- relocated from global-patterns.md by /purge, 2026-10-11 — sharpens one art, not cross-cutting -->

**Learning**: Three facts about a third-party platform are settled by its terms, not by your design, and each must be established before a lane is scoped. (1) **The compliant surface may be a different product shape.** A platform's biggest-audience surface can have no official API at all and no roadmap for one; the only legitimate integration is then a different product than the one you set out to sell (e.g. a messaging transport on the customer's own business account, not a broadcast-publish lane). Don't scope a lane around a surface until a first-party, ToS-safe API for it is proven to exist; reverse-engineered web protocols are a ban, not an integration. (2) **Per-customer credentials can be forced, not chosen.** A platform can forbid credential pooling and mandate one developer app per SaaS customer. "The customer shoulders their own API billing/quota" then stops being a pricing decision and becomes the only lawful architecture; a multi-tenant integration through your single app is not allowed. The apparent cost usually dissolves at the payload layer: where a credential store already holds one encrypted token per connection, the whole BYO credential set can be stored there as a single encrypted bundle, and adapters that receive the decrypted token per call carry the bundle unchanged, with no new table. (3) **When the customer's account is the meter, metered reads are opt-in.** On an API where reads cost money (e.g. per-metric-read pricing) and the meter is the customer's account, an unconditional periodic sweep (an hourly metrics/insights pull, say) is a silent bill run up on someone else's card. Declare metered read paths off / opt-in, never default-on; the same sweep is fine only where reads are free or billed to you.

**Apply when**: Evaluating a new platform or channel: establish the compliant API surface first and accept that the shape it forces may not match the feature you wanted to sell. A third party mandates per-tenant apps or bans shared credentials: model it as BYO-by-construction and vault the whole credential bundle in the seam that already carries a single token. Adding any recurring background fetch against a third-party API: check whether reads are metered and whose account the meter belongs to before making it default-on.

## Serverless Edge Shares Egress IPs — IP-Rate-Limited APIs Will Collide (2026-09-11)
<!-- relocated from global-patterns.md by /purge, 2026-10-11 — sharpens one art, not cross-cutting -->

**Learning**: Serverless edge platforms share outbound egress IPs across all their tenants, so any third-party API that rate-limits or bans by client IP will see your traffic pooled with strangers'. Two consequences: never do per-call session creation against such an API (persist and refresh sessions instead), and keep a non-edge egress path as break-glass for when the shared pool gets throttled or blocked. This is an unresolved property of the platform, not a bug you can wait out.

**Apply when**: Calling any per-IP-limited or per-IP-bannable third-party API from a serverless edge runtime — design for shared egress from the start.
